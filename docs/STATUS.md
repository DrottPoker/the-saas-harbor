# Implementation status

Updated 2026-09-25 with features from a competitor review (among them Paddle, Polar and Dodo Payments), a review before release, demo products, email notifications, readable addresses and sharing cards, a Content Security Policy, email links that work on any device, and reports with an admin panel. The project was reviewed and handed over 2026-09-24; the first release was built 2026-09-12 and committed on the `development` branch.

## Implemented

The first release includes accounts, email confirmation and recovery, public maker profiles, multiple editable SaaS per owner, profile/logo uploads, SaaS and maker pages, category/name filtering, newest arrivals, and a USD MRR leaderboard. Each optional metric has a sharing control. Private verification history and the current public projection are separate and protected by RLS. No demo data is displayed as real activity.

Makers can message each other privately (see Messages below), and report products, profiles and messages to the admins, who decide in an admin panel (see Reports and moderation below). They get emails about unread messages and about decisions (see Email notifications below). Other forms of connection, such as following or contact lists, are not implemented.

## Fixes from the project review 2026-10-01

At the owner's request, the whole project was reviewed for bugs, gaps and inconsistencies: the database, the payment providers, the Server Actions and routes, the public pages, the interface, and email, Telegram, the scripts and these documents. The owner chose to fix the four security findings first, then the bugs users notice and the revenue findings.

- **Dependencies.** Next.js 16.3.8 and nodemailer 10.0.13 fix security advisories published on 2026-09-30 that `npm audit` did not report yet. For Next.js these include GHSA-mcj8-r9mp-w47p, which concerns a root-level catch-all, such as the `@modal` slot, together with static routes; for nodemailer GHSA-4ffr-jq9g-5ffx and GHSA-g73g-hqqh-jr95. A high advisory in `brace-expansion`, which ESLint uses, is fixed in the lockfile. `npm run check`, `npm run build` and `npm run test:e2e` (19 tests) pass.
- **A forged Domain verified mark.** The database and browsers read `https://a.example\@b.example` differently: the app verified the record on `a.example`, while the database took the host for `b.example`. A founder could verify a domain they own, then move the website to another product's domain and keep the mark until the daily check removed it four days later, and do it again. The database now reads hosts as browsers do, a website may not hold spaces, control characters or backslashes (the form and a check constraint refuse them; none in production had any), and the product page, the Markdown and the editor show the mark only while the verified domain is still the website's domain (migration `20261001090000_website_host.sql`). pgTAP and unit tests cover the address that was read two ways.
- **Profiles made outside sign-up.** A signed-in user without a profile, such as a Google account that had not chosen a username yet, could insert a profile through the API, or have `save_profile` or `save_saas` make one, under any name. A reserved name such as `support` then became the address, no Terms acceptance was recorded, the app let the account in, and the seven-day cleanup of unfinished sign-ups no longer applied. Profiles now come only from sign-up: the trigger creates one when the sign-up carries a valid username and the accepted Terms, `complete_signup` does it at `/auth/finish`, and users hold no insert privilege; `save_profile` and `save_saas` update only (migration `20261001100000_profiles_from_signup.sql`). A sign-up made straight through the Auth API without the Terms now has no profile, and the app sends every account without one to `/auth/finish`, not only those created through Google or GitHub. No account in production lacked a profile. The browser tests and the seed create their accounts the way sign-up does. pgTAP covers the refused insert, both functions, a sign-up without the Terms or with a future version, and finishing sign-up.
- **A feedback link to another site.** The page feedback came from was checked to be a path on this site, but a tab or line break after the first slash passed, and browsers drop those, so `/feedback?from=%2F%09%2Fx.example` gave a Back to where you were link, and the admin panel a Sent from link, to `x.example`. The page now holds no spaces, control characters or backslashes, in the app and in the database, and the admin panel links a stored page only while it passes the check (migration `20261001110000_feedback_page.sql`; none in production had any). Unit tests and pgTAP cover tabs, line breaks and backslashes.

The three migrations above were applied to production on 2026-10-01, before the code. The bugs users notice and the revenue findings followed:

- **Sign-in forms that kept the last form's result.** Next.js keeps a page's state when only the query changes, so switching between sign-in, sign-up and password reset kept one form: after signing up, Create one showed Check your inbox for the old address again, and a failed sign-in's error followed to the reset form. Each form now starts afresh. Back in the username step no longer shows a green notice reading "details", the links between the forms keep where sign-in continues, and on the full sign-in page another form loads as a page instead of a dialog over it. The browser tests cover each.
- **The answer to a first connection.** The form that connects a payment provider gives way to the connected provider as soon as the page has the connection, and its answer, such as the items that were not counted, went with it; so did Disconnected. The section now keeps both answers, and the browser tests check them.
- **A logo lost on a failed save.** React resets a form after its action, failed or not, and a file field or the Remove current image box cannot be filled in again from what was sent, so a founder who chose a new logo and saved with a mistake elsewhere saved again without the logo, unaware. The product form now submits like the profile editor, without the reset; the registration browser test saves with an address the server refuses and finds the logo still chosen.
- **Telegram alerts about every second message.** A message to the owner's account is alerted once per conversation until the owner reads it. The check compared the alert's own time with the read position, which is the newest message's time; the alert is always a moment later than its message, so after reading just up to the alerted message, without replying, the next message counted as alerted already. It now compares the alerted message's time, as the message emails do (migration `20261001120000_message_alert_after_read.sql`), and pgTAP covers reading without replying.
- **Emails given up during an outage.** Every claim counted as an attempt, and an email was given up after five, so an SMTP outage of about 50 minutes, or a revoked Resend key, gave up every email queued meanwhile, decisions included, and a Telegram outage of a few minutes did the same to alerts. A failure of the service rather than of the email or alert (it cannot be reached, refuses the credentials, answers with a temporary failure or a rate limit) now puts it back without counting the attempt and stops the run, and the log names the failure's code (migration `20261001130000_outbox_deferral.sql`). Unit tests cover which failures count, and pgTAP the deferral.
- **A message sent twice.** Only the Send button was disabled while a message was sent, so Ctrl or Cmd and Enter pressed again sent the same text a second time, and anything typed meanwhile was wiped when the field reset. While a message is sent, the field is now read-only and the shortcut sends nothing.
- **An old key's figures on a new connection.** A verification or a read of payments that started with one key and finished after the founder connected another key of the same provider, such as the first read of payments right after connecting, or an hourly run, stored the old account's MRR, subscription claims and payments on the new connection. The payments then stayed in the 12-month and all-time figures and kept the old account claimed. Both writes now name the connection whose key they read, and the database refuses them once another key is connected (migration `20261001140000_connection_guard.sql`); the run tells the founder the key was replaced. The browser tests had logged such late runs when they switched providers. pgTAP covers both refusals.
- **Large accounts that never reached older payments.** Older payments were read only after the last six months had been listed in full within one run's page limit, and every run starts that listing again, so an account above about 1,000 Paddle transactions or 20,000 Stripe charges a month never got its 12-month or all-time figure. Older payments are now read whenever the listing reaches the stored payments, so such accounts get back to their first payment over several runs (their payments beyond what one run lists no longer pick up refunds). A run that runs out on a day also stores the payments it valued that day, so Dodo Payments no longer stalls on a day with more payments than one run values. Unit tests cover both.
- **Stripe MRR with tax included.** Stripe MRR took a price's amount as it is, so a tax-inclusive price (common in the EU) counted its VAT: a EUR 12 price with 20% VAT counted as EUR 12, not EUR 10, about a fifth above the same account on Paddle or Polar, while the history and growth, which come from invoices, left the tax out. The tax is now taken out, after discounts, at the share the subscription's latest invoice shows, as the other providers do; without that invoice it stays in and the founder is told.
- **A deleted Stripe coupon failed every verification.** Each coupon on a subscription is read on its own, and a coupon deleted in Stripe still discounts the subscriptions that have it but answers 404, which failed the whole verification until the product went stale. Such subscriptions are now left out of MRR, with a note to the founder; the rest verifies. Unit tests cover both, and a fake Stripe account reads them end to end. Neither has been tried against Stripe itself (known issue 1).
- **Paddle accounts with one annual subscriber.** MRR read every transaction back one full billing cycle before the oldest current period of any subscription, so one annual subscriber eleven months into its year made the read nearly two years long, and an account with about 260 transactions a month hit the limit of one run and could not verify at all, hourly runs included. MRR now reads the last 35 days for every subscription, then the charges of the subscriptions without a full one there, by their ids (`subscription_id`), each back one cycle. A unit test checks which subscriptions are asked for. Polar, Chargebee and Whop read the same kind of wide window, at a larger limit (known issue 26).

The migrations of the second part were applied to production on 2026-10-01 too, before the code, and `npx supabase db diff --linked` reports no changes. With every fix in place, `npm run check` (464 unit tests), `npm run build`, the 673 pgTAP tests and `npm run test:e2e` (19 tests) pass. The pgTAP files ran through `psql` in the database container, since Docker Desktop had stopped forwarding the local stack's ports and `npm run test:db` could not connect until `npm run db:restart`.

The pages say Not shared for all of them. The owner chose to keep the API as it is.

An email sign-up whose address was never confirmed kept the address and its username for good, and a sign-up made straight through the Auth API without the Terms was never removed. At the owner's request, the daily cleanup now deletes any account whose email address is still unconfirmed, or that still has no profile, seven days after it was created, unless it has uploaded images, products or admin rights; this frees the address and the username (migration `20261001150000_unfinished_signups.sql`). Until then, the profile of an unconfirmed sign-up stays readable at its address, though it holds only the username, is not indexed and is not in the sitemap.
- **A visit's time with an account's source.** An account's source kept when its visit began: the time of the visit's first page view, to the microsecond, which found the account's visits in the site statistics, although the privacy policy keeps those apart from accounts. Nothing showed it, and it is gone from the table and from `admin_account` (migration `20261001160000_account_source_visit_time.sql`). pgTAP checks that a source holds only where the visit came from.
- **The privacy policy and the Terms.** The privacy policy (updated 2026-10-01) now says what the Telegram alerts carry (the name and username of the account, the founder, the reporter or the sender of feedback, whether an email address is confirmed, what or whom a report is about, a product's name, tagline and category, and the page feedback was sent from), that short-lived cookies carry a sign-in with Google or GitHub and a Gumroad connection, that Gumroad connects through access the founder grants rather than a key, and that unfinished sign-ups are deleted after about a week. - **A check that outlived its connection.** A run that finished after the founder disconnected the provider, as the browser tests do when they switch providers, was logged as an unexpected failure. It now ends like a run whose key was replaced: nothing is stored, and the answer says why (`changedDuringCheck` in `src/lib/revenue/errors.ts`, with a unit test).

Both migrations were applied to production on 2026-10-01, before the code, and `npx supabase db diff --linked` reports no changes; the cleanup found no account to delete there. `npm run check` (466 unit tests), `npm run build`, the 676 pgTAP tests and `npm run test:e2e` (19 tests) pass, and the revenue browser tests passed again after the change for checks that outlive their connection.

- **One Node.js version.** `engines` allowed any Node.js from 22.14, so Vercel most likely ran Node 24 while CI and `.nvmrc` used 22. ## Read receipts in messages 2026-09-28

## More precise site statistics 2026-09-27

- System versions. Crawlers that do not run JavaScript, such as those of ChatGPT, Claude and Perplexity, and text extractors that drop hidden elements, saw little more than the placeholder. Public pages now have no `loading.tsx` and arrive complete; the dashboard, messages and the admin panel keep the placeholder. Moving between public pages now waits for the next page (0.3 to 0.5 seconds on the live site, measured from Sweden) instead of showing the placeholder first.
- **Metadata was in the body.** Next.js streams the title, description and canonical link into the body for every user agent except a list of known bots (Bingbot among them, not Googlebot or the AI crawlers). Google reads it once it has rendered the page and a script has moved it into the head; crawlers that do not render miss it. `htmlLimitedBots: /.*/` now puts it in the head of every response.
- **Missing pages answered 200.** A missing product, profile, category or technology now answers 404, and a renamed product's earlier address a real 308, since nothing is streamed before the page knows. The HTML of a 404 is then Next.js's bare error document, and the browser draws the not-found page, with the header, footer and saved theme, once the scripts load; before, the header and footer came first and the not-found text followed in the same way.
- **A second copy of the site** answered at `the-saas-harbor.vercel.app`. Production now redirects every other host to `NEXT_PUBLIC_SITE_URL`, except `/api/` for the scheduled jobs.
- **No favicon file, Apple touch icon or organization data.** `/favicon.ico` (16, 32 and 48 pixels), the Apple touch icon and a 512-pixel `/logo.png` are drawn from the logo, and the home page describes the organization, its logo and the site as one graph, and the leaderboard's first page as a list.
- **Titles and descriptions.** Browse, New arrivals, How it works, Privacy and Terms had the site's sharing title and some the site's description; every public page now sets its own. The home page is titled Free SaaS directory and verified MRR leaderboard, with a description that says listing is free and how to reach the leaderboard; Browse is Browse SaaS products and New arrivals New SaaS products in titles (the headings are unchanged). Search results pages are `noindex, follow`, later pages of a list are pages of their own, and profiles without products, a headline and an About section stay out of search results. The root layout allows large image previews and snippets of any length.
- **IndexNow.** Production announces product pages to Bing, Yandex, Seznam, Naver and the other IndexNow search engines when founders save or delete them. Bing's index also serves ChatGPT search, Copilot and DuckDuckGo.
- **llms.txt** now says that listing is free, without payment details, that connecting a payment provider is optional and ranks the product, and where founders sign up.

## Features from the competitor review 2026-09-25

## Release review 2026-09-25

The project owner asked for an inspection before release: security, bugs, and whether everything works. Three reviews (the database, the application's security, and functional bugs) were checked against the code and the local database. A production build was inspected in the browser, its headers checked, and the dependencies and the whole git history searched for known flaws and committed secrets. Every confirmed defect below was fixed with a test.

- **Critical, dependency:** Next.js 16.3.5 had a remote code execution flaw in `next/og` ImageResponse (CVE-2026-94545), which the sharing cards use with text makers write. `npm audit` did not report it yet. Next.js is now 16.3.6.
- **Database** (migration `20260925190000_release_hardening.sql`):
  - Renaming a product could reserve any number of slugs. A slug in use now wins over a redirect, and a product keeps five earlier slugs.
  - Deleting and adding a product reset the daily limit. Additions are now counted in their own log.
  - Parallel requests could exceed the message and report limits. They now count one at a time.
  - An image path could climb into another folder with `..`.
  - `send_message` told a suspended recipient apart from a deleted one.
  - New objects in `public` were open to the API roles by default, and the public views held write privileges. Both are closed, and a new test lists every privilege.
  - Account deletion left the maker's id in other makers' queued emails and live-update events.
- **Application:**
  - Stripe checks were not limited, and failed checks never were. Now a product refreshes at most every five minutes, and a maker starts at most 20 checks an hour.
  - Database and internal error messages reached makers.
  - Session cookies lacked `Secure`, and any signed-in session could set a new password. Cookies are `Secure` over https, a new password needs a fresh reset link, and other sessions end.
  - Images could unpack to huge sizes. They are now limited to 4096 pixels per side.
  - The proxy's redirects from ids could be cached forever.
  - The CSP blocked the script on the global error page.
  - Stripe and exchange-rate overrides could use http in production.
- **Bugs:**
  - A message email never came after the recipient had read the previous message without replying.
  - Accounts with more than 20,000 invoices failed verification entirely. History is now skipped with a note, and the note names the permission that is missing.
  - Multi-currency prices were valued in the price's default currency.
  - A repeated search parameter crashed the list pages, and a page past the last showed an error.
  - The category reset after a failed save.
  - Prorations were spread over an average month instead of their billing period.
  - Weekly prices differed between the MRR and the history.
  - The chart could show $2.50 steps.
  - A long disconnection could leave gaps in an open conversation, and a reconnect did not catch up.
  - Long names without spaces overflowed on phones.
  - Launch dates accepted year 0 and the future.
  - Roles "this month" were refused east of UTC.
  - The sitemap and the daily Stripe sync stopped at 1,000 rows.
  - Browse was titled "Discover".

Decisions the owner made on 2026-09-25: the first two wait until later (known issues 13 and 18), and the production Auth settings in the third are agreed and apply when production is set up (known issue 4).

1. **Faked revenue.** A maker can create subscriptions in their own live Stripe account that are never paid. Sent but unpaid invoices keep a subscription active, and invoices marked paid outside Stripe count as paid, so they show as verified MRR. Counting only subscriptions whose latest invoice was paid by an actual payment would close this. It changes the MRR definition, since past-due and unpaid invoiced subscriptions would no longer count.
2. **Sign-in abuse.** Sign-in, sign-up and password reset run on the server, so Supabase Auth sees the server's address. Its limits per address then apply to all users together or not at all, depending on the host. A CAPTCHA on these forms (for example Cloudflare Turnstile or hCaptcha) is the usual fix. It needs an account with the provider and a line in the CSP.
3. **Production Auth settings** (known issue 4). Allow at least 60 seconds between emails to one address (`max_frequency`; it is 1 second locally for the tests), turn `secure_password_change` on, and set email rate limits for the SMTP provider.

Accepted and documented:

- A maker may delete a hidden product and add it again. The right to delete comes first, and the daily limit, reports and suspension still apply.
- Makers can upload files straight to their own storage folder through the Storage API, which checks only the type and size.
- A maker's name appears in message email subjects.
- A confirmation link that an attacker sends can sign the reader into the attacker's account.

7. One provider account verifies one product, and a product has one provider. Makers who sell several products from one account need a per-product filter (product ids, or Dodo's brands) to split revenue, and those who sell one product through two providers need connections added together.
8. Stripe, Paddle, Polar, Dodo Payments, Creem, Chargebee, Whop and RevenueCat are supported. Lemon Squeezy was left out on purpose: its API keys always have full access (checked again 2026-09-27). Superwall and Mollie were left out too (see More payment providers); a Superwall app can connect RevenueCat or Stripe where it uses them. A founder who connects RevenueCat for one product and the Stripe or Paddle account RevenueCat also tracks for another is not stopped, since RevenueCat products claim their project rather than subscriptions. Requests to a provider are spaced out per server process only; with several app instances, Paddle's limit per IP address is shared between them.
9. Encryption key rotation: stored keys carry a version prefix, but there is no re-encryption job yet.
10. Search engines: add the site to Google Search Console and Bing Webmaster Tools and submit the sitemap (README, Production), then check the home page and a product page with Google's Rich Results Test. Product pages describe a `SoftwareApplication` without a price or ratings, which Google needs for a rich result, so Search Console may list them as incomplete; that does not affect indexing. Private pages still stream under their placeholder and answer 200 with `noindex` for what is missing, which crawlers never see.
11. Old images stay in storage after replacement or removal, until the account is deleted. There is no limit on how many files a maker stores in their folder; a cleanup of unreferenced files should come before a per-maker limit, so replacing a logo never fills it up.
12. All routes are dynamic with `no-store`. Public pages could be cached once traffic grows, with private data kept separate. The nonce-based Content Security Policy needs a fresh render per request, so caching pages would mean moving to hashes or the experimental SRI support first.
13. Faked revenue through the maker's own Stripe account (see Release review, point 1). Postponed by the owner. Paddle already values subscriptions by their paid charges; Polar and Dodo Payments count subscriptions as the provider reports them.
14. Realtime keeps its message and read event rows, which hold ids and times only, for a few days.
15. Notification emails have no one-click unsubscribe (`List-Unsubscribe`, RFC 8058): turning them off takes a sign-in. Large senders to Gmail and Yahoo need it, so add it before volumes grow. The emails are in English only.
16. Demo products retire themselves at 12 ranked products, but their code stays. Remove it once the directory has grown; ARCHITECTURE lists the parts.

23. Revenue from payments has not been tried against real accounts either. Open points from the documentation: Stripe's permission ids `rak_charge_read`, `rak_checkout_session_read` and `rak_dispute_read`, and whether Stripe still fills in a new key's permissions from the link at all; whether a lost Stripe dispute also changes the charge's refunded amount (then it would be taken off twice); whether Paddle's adjusted totals include adjustments still awaiting approval; Dodo's list order, whether its `created_at_lte` is inclusive and whether a refund's amount includes tax; Creem's time unit (read as milliseconds or seconds) and whether its transaction list reaches back to the first transaction; Whop's `order` and `direction` parameters; and whether RevenueCat's revenue chart takes a year per request, and which of its revenue measures the chart lists first. A refund of a payment older than six months is not picked up, and a day on which RevenueCat's refunds outweigh its revenue counts as nothing rather than less. Existing Stripe connections need a new key with the three new permissions before their revenue shows.
24. Gumroad has not been tried against a real account either. Its API documents neither rate limits nor the token information endpoint's shape (read as Doorkeeper's `scope` list), and gives ten sales a request, so a large membership costs many requests each hour. Whether Gumroad applies the PKCE challenge, and whether the sales summary's day keys and its exclusion of test sales match the dashboard, are open. Revenue days follow the seller's time zone rather than UTC, and lost chargebacks are not taken off, since a token that can only view sales cannot read them. A seller's own sales tax (not the tax Gumroad collects) stays in the figures, as the API gives no share for it.
25. Shopify is planned for later (the owner's decision of 2026-09-28), the way TrustMRR does it: its "TrustMRR Revenue" app (since July 2026) is a public Shopify App Store app that a store owner installs with read access to orders, and it shows the store's sales over 7, 30 and 90 days, a year and all time. It gives sales, not MRR, so such a store would show MRR as Not shared and have no rank on the leaderboard; how stores are shown is still to be decided. The owner needs to create a Shopify Partner account and the app, request access to protected customer data (orders hold customer details) and `read_all_orders` for more than 60 days of history, and pass Shopify's app review. The app needs Shopify's mandatory privacy webhooks (`customers/data_request`, `customers/redact`, `shop/redact`) and a section in the privacy policy. New public apps may only use the GraphQL Admin API, which takes POST requests, so provider clients need an exception to the GET rule for fixed queries under a read-only scope, as for the Gumroad code exchange. Revenue from Shopify apps (the Partner API) was ruled out: the only permission that reads transactions, View financials, also allows `appCreditCreate` and `appSubscriptionCancel`, so the token cannot be limited to reading, as with Lemon Squeezy. Checked 2026-09-28 against Partner API 2026-07 and the Shopify App Store listing.
26. Polar, Chargebee and Whop still read every order, invoice or payment back one full billing cycle before the oldest current period of a counted subscription, so one annual subscriber makes the MRR read nearly two years long, and an account above about 800 a month (20,000 in one run) cannot verify, as Paddle could not before 2026-10-01. Paddle now looks up the other subscriptions' charges by their ids. The same needs a filter by subscription for each: Chargebee documents `subscription_id[in]`, whose list format should be tried against a real site first, and Polar's orders and Whop's payments have no such filter that their documentation confirms.
