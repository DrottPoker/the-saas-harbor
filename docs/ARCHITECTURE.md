# Architecture

One Next.js App Router application uses React, TypeScript, Tailwind CSS and shadcn/ui. Supabase provides PostgreSQL, email/password authentication and public image storage. Public pages use server rendering and are sent complete: only the dashboard, messages and the admin panel have a `loading.tsx` (`PageSkeleton`), so crawlers that do not run JavaScript read public pages in full, and `notFound()` and `permanentRedirect()` there answer with a real 404 or 308 (see Search engines and AI assistants). Mutations use Server Actions with fresh `getUser()` checks; a Proxy refreshes the session cookies using `getClaims()`. `currentUser()` and the public detail loaders (`publicSaas`, `publicProfile`) are wrapped in React `cache()`, so the layout, `generateMetadata` and the page share one round trip per request. `error.tsx` offers `retry()`, which re-fetches server data, and `global-error.tsx` covers failures in the root layout.

Every exposed table has RLS and explicit grants. Views use `security_invoker = true`. Composite foreign keys prevent attaching another owner's data to a product. Makers hold column grants on `profiles` and `saas` for exactly the fields they edit, so ids, `created_at` and the moderation columns are out of their reach; before these grants, a direct API insert could date a product into the future and keep it first in New arrivals. Hidden products and suspended profiles are left out of the public access above, and admins can read every row; see Reports and moderation. The invoker `save_saas` RPC saves product details, the tech stack, visibility choices and launch date; it accepts no figures. The product form shows each choice as a box that hides the figure (`hide_mrr`, `hide_revenue`, `hide_customers`, `hide_launch`), all clear on a new product, and `saveSaas` stores the opposite in the `share_*` columns, so figures are public unless the founder hides them. The columns themselves still default to `false`, so a row written without a choice keeps its figures private. Its last two parameters, the tech stack and the revenue sharing choice, are optional, and a save without them keeps the saved values, so code that predates them keeps working. Verified figures are written only by trusted server code with the service-role key, through `record_revenue_verification`, which is executable by `service_role` alone.

`supabase/tests/database/privileges.test.sql` lists every table, column and function privilege that `anon` and `authenticated` hold in `public`, and fails on anything else, so a migration that forgets a revoke cannot expose a new object unnoticed. Since migration `20260925190000_release_hardening.sql`, objects created later in `public` get no privileges for those roles until a migration grants them; functions still need their own `revoke execute ... from public`, because Postgres grants EXECUTE to PUBLIC globally. The public views are read-only for both roles.

The public projection `public_metrics` is maintained by `private.refresh_public_metrics`, called from triggers on `saas_settings`, `revenue_snapshots` and `revenue_connections`. It and its trigger function are SECURITY DEFINER, because a maker's own setting change must update a table the maker cannot write. They live in the unexposed `private` schema, has an empty `search_path`, and its execute privilege is revoked from API roles. An unset sharing flag writes NULL into the projection. Snapshots carry an identity `seq` so "latest" is deterministic even for snapshots taken at the same instant.

Public reads deliberately create a separate anonymous Supabase client. They do not inherit the current owner's session. This makes the public route's data shape identical for an owner and a visitor. All application routes are dynamic; data fetches use `no-store`, and the Proxy sends `Cache-Control: private, no-store`. The embeddable badge is the exception: it shows only public figures and may be cached for ten minutes (see Addresses and sharing). No shared application/CDN cache holds private records. An already downloaded public page cannot be recalled from a visitor.

## Revenue and discovery

MRR is stored as integer USD cents (at most 999,999,999,999, below JavaScript's safe integer limit) and only ever comes from revenue verification through a payment provider; see below. Revenue besides MRR (the last 30 days, the last 12 months and all time, see Revenue from payments) is stored the same way. Verified revenue, paying customers and launch date have independent visibility switches; revenue is one switch (`share_revenue`) for MRR and revenue from payments alike, at the owner's request of 2026-10-01 (migration `20261001220000_one_revenue_choice.sql`, which hid both for products that had hidden either). A verification older than seven days is hidden by the `public_saas` view and marked `stale`, so it leaves the leaderboard. `revenue_status` is `verified`, `private`, `stale` or `unverified`. The MRR history (`mrr_history`, twelve month-end values), 30-day growth (`mrr_growth_pct`) and revenue by month (`revenue_history`, see Revenue from payments) are public only while revenue is shared and fresh. Public pages, cards and the Markdown versions never tell visitors whether a product is `private`, `stale` or `unverified`: any figure they do not get reads Not shared, and the verification line ("Verified with Stripe...") and the Verified revenue label appear only while MRR or revenue is verified and shared. Founders see their own status in the dashboard, and admins see every product's latest figures, private ones included, in the admin panel (see Reports and moderation). A domain may still read Not verified.

The leaderboard is ordered in PostgreSQL by public MRR descending, then creation time ascending, then UUID ascending. Ties receive deterministic sequential positions. With `?by=30d`, `12m` or `all` it ranks by revenue over that window instead: the `revenue_leaderboard` view gives each product that shares a revenue figure a rank per window (`rank_30d`, `rank_12m`, `rank_total`, null for a figure it does not share), ordered the same way, while it shares its revenue. `Explore` shows the choice of ranking above the categories and keeps it in the category, search and page links; the Leaderboard table then names the window over its figure column, shows no growth, and draws revenue by month as the trend line. Beside the ranked figure every row shows revenue of all time, or MRR in the all-time ranking, with Not shared for a figure the product does not share. Phones show the ranked figure only; the second figure and the category join from 768 px, the trend line from 1024 px and the verification date from 1280 px. Each revenue ranking has its own title, description and canonical address (`/?by=all`), and only the MRR ranking carries the ItemList JSON-LD. Category and technology filters preserve the global rank. Browse includes products without shared MRR and orders by name. New arrivals orders by creation time descending. List queries return at most 12 rows per page. The server validates category and page inputs and searches product names case-insensitively. User-supplied wildcard characters (`%`, `_`, `*` and backslash) are removed first, since PostgREST treats `*` like `%`.

The home page speaks to founders. `Explore` opens the leaderboard with `FounderHeader` (`src/components/founder-header.tsx`): the heading Get your SaaS seen. List it for free., a sentence that every SaaS is welcome, verified or not, and that connecting a payment provider is optional, a button to list a product (sign-up for visitors, the product form for signed-in users) and a link to How it works. Beside it, a card headed Free for every SaaS lists what a listing gives (a page, a link to the site, page views and messages, and a place on the leaderboard with connected revenue) and says that no payment details or revenue check are needed. The list follows under a slim Leaderboard heading with the search.

## Demo products

`src/lib/demo.ts` holds fifteen made-up products with makers, logos, descriptions and figures, so a first visitor sees what listings look like instead of an empty directory. They exist only in code, never in the database, so nothing that reads data (the ranking, the sitemap, maker pages, the admin panel, the sharing card's figures) can take them for real products.

- **When.** `demoActive()` in `src/lib/data.ts` counts the leaderboard. Demo products show while fewer than a page (12) of real products share verified MRR, and never with `DEMO_PRODUCTS=off`. When the count cannot be read, they stay hidden.
- **Where.** `Explore` asks `demoRows()` for the demo products that match the list's category and search, on the first page only, and only as many as the real products leave free on it, so each real product that joins takes one demo place. They follow the real products in their own section, headed Demo products, as a table on the leaderboard and as cards in Browse and New arrivals. A ranking takes only those that share its figure, highest first and without ranks; New arrivals orders them by launch date, since they never joined. Their made-up revenue besides MRR (`demoRevenue`) follows their MRR and history, and stays the same all month.
- **Marking.** At the owner's request (2026-09-26), leaderboard rows carry no badge and the list has no visible heading or explanation: they are marked by the Demo MRR column (also read out to screen readers on each row), by having no rank, and by an `sr-only` Demo products heading. Cards in Browse and New arrivals and every demo page carry a Demo badge; the page no longer has the explanatory notice. Their revenue status is never `verified`, their figures never carry the verified mark and are called Demo MRR or made up, and they have no website, maker account or maker page, and no Send message or Report. Their logos are drawn in `src/components/demo-logo.tsx`, and their 12-month history is generated per month from a starting level, so charts and 30-day growth behave like real ones.
- **Pages.** `/demo/<slug>` renders the same `ProductProfile` component as `/saas/<slug>`, with a notice at the top and `noindex, nofollow`, and answers 404 once demo products are gone. How it works explains them while they show.
- **Removing them** for good means deleting `src/lib/demo.ts`, `demo-logo.tsx` and the `/demo` route, the demo functions in `data.ts`, the `demo` branches in `listings.tsx`, `explore.tsx` and `ProductProfile`, and their tests.

## Revenue verification

Makers connect one payment provider per product: Stripe, Paddle, Polar, Dodo Payments, Creem, Chargebee, Whop or RevenueCat, each with a key that can only read, or Gumroad, by approving read access to its sales through OAuth (migration `20260925230000_payment_providers.sql` made the Stripe-only names provider-neutral, `20260927100000_more_payment_providers.sql` added Creem, Chargebee, Whop and RevenueCat, and `20260928090000_gumroad.sql` Gumroad). The flow lives in `src/lib/revenue`, with one folder per provider:

- `catalog.ts` names the providers and their key labels, for the browser as well, with the second field a key needs where it belongs to a Chargebee site or a RevenueCat project, and `providerList()` for copy that names them all. `providers.ts` maps each to its adapter (`types.ts`): `parseKey` validates a pasted key and that field, and `read` reads the account and returns MRR per currency, paying customers, the counted subscription ids, what could not be counted, and service lines for the history (or none, with a note). A site or project is stored with its key as one encrypted value (`account-key.ts`), so every later verification reads the same account. The editor shows each provider's steps in a box that links to the page where the key is made.
- `http.ts` sends only GET requests, with a timeout, and spaces requests to one provider at least 500 ms (Chargebee), 300 ms (Paddle, Dodo), 150 ms (Polar, Creem) or 100 ms (Whop, Gumroad) apart in each process: Paddle limits each IP address to 240 requests a minute, Chargebee each site to 150 on its smallest plan, and the others each account. RevenueCat allows 25 chart requests a minute per project, and a run that also reads the revenue chart back to its first year sends fewer than 20, so its requests are not spaced. Overrides of the provider and exchange-rate addresses, used by the tests' fake server (`tests/e2e/fake-providers.mjs`, `fake-billing.mjs`, `fake-billing-extra.mjs` and `fake-gumroad.mjs`), must use https, or plain http to this machine (`isSecureOrLocalUrl` in `src/lib/loopback.ts`), in every environment, so the browser tests can run against a production build while a wrong setting still cannot send keys in the clear; Paddle, Polar, Dodo, Creem and Whop add `/live` or `/test` to theirs, and Chargebee the site. The Telegram address follows the same rule, since the bot token travels in it, and SMTP requires TLS except on this machine.
- `money.ts` normalizes billing intervals to months (a day or week by the average month of 365.25 / 12 days) and converts per-currency totals to USD cents, rounding once. `periodMonths()` counts a service period in calendar months where it runs to the same date a whole number of months later (within a day), so a monthly charge covers one month in February too, and by the average month otherwise; `toMinorUnits()` reads amounts that providers give in major units. `history.ts` is pure and unit-tested: MRR at an instant is the sum of the paid recurring charges whose service period covers it, the way revenue analytics tools reconstruct it. Each provider turns its invoices, transactions or orders into service lines. The last twelve month-ends give the chart, and MRR from charges now against 30 days ago gives the 30-day growth, so both sides of the comparison use the same method. History is converted at today's rates, so the chart shows the business rather than currency moves.
- `fx.ts` converts other currencies to USD with Frankfurter's daily central-bank rates (base USD). A currency without a rate fails the verification instead of being dropped.
- `crypto.ts` stores keys with AES-256-GCM under `STRIPE_KEY_ENCRYPTION_KEY` (the name predates the other providers and stays, since changing the secret needs a re-encryption plan), bound to the SaaS id as associated data. The stored format carries a version prefix for later key rotation. Owners can never read the ciphertext: `encrypted_key` is excluded from their column grants.
- `sync.ts` verifies before storing anything, then calls `record_revenue_verification`, which stores the provider and key, claims the counted subscriptions, records a snapshot (with the provider, the history and the MRR from charges now and 30 days ago) and updates the connection in one transaction. A new key may switch the product to another provider; a re-verification must come from the connected one. A subscription can verify one SaaS only (`private.subscription_claims`, the SHA-256 of the subscription id, prefixed with the provider's name for providers other than Stripe), so one account cannot be counted twice. Failed re-verifications record a readable error for the owner and keep the last snapshot until it goes stale. A re-verification, and every read of payments (`record_revenue_payments`), passes the `connected_at` of the connection whose key it read, and the database refuses the write once another key has been connected since (migration `20261001140000_connection_guard.sql`): before, a run that started with one key and finished after the founder connected another of the same provider wrote the old account's figures, claims and payments onto the new connection. `changedDuringCheck` (`src/lib/revenue/errors.ts`) turns that refusal, and the one for a provider disconnected since the run began, into a `VerificationError`, so such a run stores nothing and is not logged as a failure. Disconnecting deletes the connection through the founder's own session, which the policy `connections_owner_delete` limits to the owner, not through the service role; its key, subscription claims and payments go with it, and the trigger refreshes the public projection.

MRR has one definition for every provider: active and past-due subscriptions, their recurring charge normalized to a month, after ongoing discounts, before tax. Trials, paused subscriptions, one-time discounts and usage-based charges are excluded, and paying customers are customers with a subscription worth more than zero. What each provider gives decides how it is read:

- **Stripe** (`rk_live_`; `rk_test_` only when `REVENUE_ALLOW_TEST_KEYS=true`), with Read for Subscriptions, Invoices, Coupons and Prices. Secret and publishable keys are rejected. The editor links to Stripe's form for a new restricted key with the name and those four permissions filled in (`stripeKeyCreationUrl` in `stripe/key.ts`, with the ids `rak_subscription_read`, `rak_invoice_read`, `rak_coupon_read` and `rak_plan_read`, which Prices still use). Stripe does not document these parameters, so the editor also names the permissions to check. `stripe/client.ts` reads active and past-due subscriptions with expanded discounts, then the coupons and tiered prices they reference, and paid invoices from the last 25 months with all their lines and the prices those lines use; every request pins `Stripe-Version: 2026-08-26.dahlia`. `stripe/mrr.ts` values licensed items (per-unit and volume or graduated tiers, quantity transforms, forever and repeating discounts in percent or amount), and a multi-currency price by its amount in the subscription's currency (`currency_options`). `stripe/history.ts` counts each subscription line's net amount (after discounts and inclusive tax) over its service period, full periods by the price's billing interval and prorations at their share of the billing period they fall in. A price that includes tax (`tax_behavior` inclusive under Stripe Tax, or a tax rate set as inclusive) is taken without its tax, after discounts, at the share the subscription's latest invoice shows (what its lines charged less the tax they included, over what they charged), for up to 200 such subscriptions a run; without that invoice the tax stays in and the founder is told (`mrrNote`). A coupon deleted in Stripe keeps discounting the subscriptions that have it, but Stripe answers 404 for it, so those subscriptions are left out of MRR, still claimed, and the founder is told, rather than the whole verification failing. Invoice history is extra: a key without Invoices or Prices access, or an account with more invoices than one run reads (200 pages), still verifies MRR, and the note names the missing permission.
- **Paddle** Billing (`pdl_live_apikey_`; `pdl_sdbx_apikey_` only with test keys allowed), with Read for Subscriptions and Transactions. Legacy keys, which have full access, are rejected. Paddle bills in local prices and converted currencies and adds or includes tax when it bills, which a subscription's prices do not show, so `paddle/mrr.ts` values each active or past-due subscription by its latest paid transaction for a full billing period (lines with a recurring price and no proration, or a proration rate of 1): the line totals less tax, and without a discount that has ended since (the subscription has no discount, a one-off one, or one whose end has passed). A subscription without such a charge, such as one imported into Paddle, is not counted and the maker is told. Transactions from the last 25 months serve MRR and the history, where every recurring line counts over its period and a proration at the full period's rate. Without the history (the hourly run), or for an account with more transactions than one run reads, MRR reads the transactions of the last 35 days, which hold the latest charge of every monthly subscription that is paid up, then asks for the charges of the other subscriptions by their ids (`subscription_id`, 25 a request, up to 1,000 subscriptions), each back one billing cycle before its current period. Before, one annual subscription widened the read for every subscription to nearly two years, so a mid-size account with one annual subscriber could not verify at all. Requests pin `Paddle-Version: 1`, and the cursor's next page is built from its `after` value, so requests only go to Paddle's own address.
- **Polar** (`polar_oat_` organization access tokens), with the scopes organizations:read, subscriptions:read and orders:read. Sandbox and production tokens look alike, so a new token is tried on production first and on the sandbox where test keys are allowed. `polar/mrr.ts` takes each active or past-due subscription's amount, which is its prices less its current discount and without metered usage, adds back a discount for the first period only, and takes out tax where prices included it, at the share the subscription's latest paid order shows (an order whose total equals its subtotal less discounts included tax). The history counts each item of paid subscription orders over its own period at the order's net share of its subtotal, which removes discounts and tax either way, leaving metered prices out. Requests pin `Polar-Version: 2026-10`.
- **Dodo Payments**, with a key whose write access is turned off. Dodo documents no key format, so only keys that plainly belong to another provider are refused, and the environment is found like Polar's. `dodo/mrr.ts` takes each active or past-due subscription's recurring charge (`recurring_pre_tax_amount`), leaving out trials, on-demand subscriptions and those on hold or paused. Where the charge includes tax, the tax is taken out at the share the subscription's latest successful payment shows, two requests each and at most 200 subscriptions a run. Dodo's payments do not say which period they cover, so these products have no history or 30-day growth.
- **Creem** (`creem_` live keys; `creem_test_` only with test keys allowed), with read scopes for products, subscriptions and transactions. Creem 2.0 has keys with scopes, but documents neither the scope names nor a way to read a key's scopes, so the editor asks for read scopes only, as with Dodo. A Creem subscription does not carry its price: `creem/mrr.ts` values each active, past-due or scheduled-to-cancel subscription by its product's price times its units, less a discount that lasts beyond the first period (percent or amount), without metered usage. Where the product's price includes tax, the tax is taken out at the share the subscription's latest paid transaction shows; the list gives that transaction or a lookup per subscription does (at most 200), and a subscription without one is not counted. The subscription list and the transaction list have no filters, so both are read whole. The history counts each paid subscription transaction over its own period, after discounts and without tax, and leaves out subscriptions to products with metered usage, whose charges mix usage with the price.
- **Chargebee** (a read-only key, with access to all data or restricted to transactional data, and the site: the name before `.chargebee.com`, taken from a pasted address too; a test site's name ends in `-test`), through `https://<site>.chargebee.com/api/v2` with the key as the Basic username. Chargebee cannot say through its API what kind of key it is, so the editor asks for a read-only one. It has no past-due status (a subscription whose payment failed stays active), so active and non-renewing subscriptions are counted. Prices may include tax depending on the site and the customer, which only invoices show, so `chargebee/mrr.ts` values each subscription like Paddle: its latest paid invoice with a full cycle of its plan, whose plan and addon lines (not metered, not one-time charges) count after the coupons and discounts the subscription still has and without included tax, each line by its own period. Credits are not discounts and are added back. The history counts plan and addon lines of paid invoices from the last 25 months over their periods, which counts a prorated line at its full rate.
- **Whop** (an account API key, for which Whop documents no format). A new key is tried on production first and on the sandbox where test keys are allowed, and every verification asks Whop which permissions the key holds on its account (`GET /permissions`) and refuses it if any is more than a read. The key's account is the oldest one it can list, which needs no permission. Requests pin `Api-Version-Date: 2026-09-25`, since Whop changes its API often. A membership does not carry its price: `whop/mrr.ts` values an active or past-due membership that is not paused by its latest paid renewal on the same plan (the total less tax), or in its first period by its plan's renewal price, less the promo code of its first payment where that lasts beyond the first payment, and without included tax at the share that payment shows. Plans bill every so many days; 30 days count as a month and 365 as a year. One-time plans are not counted. Payments do not say which period they cover, so the history counts each paid subscription payment over one billing period of its plan from when it was paid, and leaves out payments for plan changes.
- **RevenueCat** (a V2 secret key, `sk_`, with Charts & metrics read only, and the project ID, taken from a pasted dashboard address too), for app store subscriptions. A key limited to charts cannot read subscriptions or their prices, and RevenueCat cannot say whether other access only reads, so every verification checks that the key is refused the project list and the project's customers, and refuses the key otherwise. MRR comes from RevenueCat's own daily MRR chart in USD, before tax where the chart's options offer `revenue_net_of_taxes`, and paying customers from its active subscriptions chart. RevenueCat's MRR differs from the definition above: it counts introductory and promotional prices as charged, leaves out subscriptions in billing retry, and counts subscriptions rather than customers; How it works says so. The history and 30-day growth use the same daily MRR chart over the last thirteen months. A product claims the project (`project:<id>`) rather than subscriptions, since a key limited to charts sees none.
- **Gumroad** (no key: OAuth, see below). Gumroad calls the subscriptions to membership products subscribers, and its API does not show what a subscriber pays, so `gumroad/mrr.ts` values each active subscriber (alive, set to cancel at the end of the period, or with a payment being retried, and past any free trial) by its latest sale for a whole period: the sale's price, in US cents after discounts and without the tax Gumroad collects, over the period it pays for (monthly, quarterly, every six months, yearly or every two years). Sales for an upgrade cover part of a period and are skipped; installment plans pay for products that are not memberships and are not counted. The sales list gives ten sales a request, newest first, so a scheduled verification reads each membership's sales back only until every subscriber has one, over at most a billing period and a month. The history counts each such charge over its period, from the last 25 months of sales; an account with more sales than one run reads has no history, with a note. Every verification checks the token's scopes (`/oauth/token/info`) and refuses anything beyond reading sales.

### Revenue from payments

Besides MRR, a product has revenue for the last 30 days (today and the 29 days before, in UTC), the last 12 months (from the day after the same date a year ago) and all time. It counts every payment, subscriptions and one-time purchases alike, after discounts, less refunds and lost disputes, and before tax and the provider's fees, on the UTC day it was paid. The figures are USD cents at the day's rates, like the history, and are shared with MRR (`share_revenue`). Migration `20260927170000_revenue.sql` adds all of it.

- **Storage.** `private.revenue_payments` holds one row per payment: the SHA-256 of `payment:<provider>:<id>` as its key, the day, the currency, what it earned in minor units, a fingerprint that changes whenever that amount could have, such as after a refund, and its `kind`: `subscription`, `one_time`, or `unknown` for providers that give daily totals only (migration `20261001210000_revenue_by_month.sql`). It holds no customer data. The key is the claim: one payment verifies one product, and `record_revenue_payments` refuses a payment that another product holds. Rows reference `revenue_connections`, so disconnecting or deleting the product removes them, and `record_revenue_verification` deletes them for a new key, which may be another account. The connection records how far they reach: from `revenue_from`, or all time once `revenue_origin` is set, up to `revenue_read_at`, with `revenue_checked_at` for the last attempt and `revenue_note` for a failure the founder sees.
- **Reading.** Each adapter's `payments()` lists the paid payments of a window of time newest first, for at most a number of pages, and says whether it reached the window's start. `collectPayments` in `payments.ts` (pure and unit-tested) lists the last 183 days again on every read, which picks up refunds, then, once they are complete or reach the stored payments, reads older payments back from where the stored ones start, 100 pages a run, until the account's first payment. An account too large to list six months in one run therefore still reaches its first payment over several runs, though its payments from beyond what one run re-reads no longer pick up refunds. An unfinished list covers the days after its oldest payment's day, since the next page may hold more of that day; the payments it listed on that day are stored all the same, outside the windows, so they need no valuing again and count once the day is read in full. A read that cannot list the six months in one go covers what it can and goes on in the next run, because stored payments are not valued again: `revenue_read_state` gives the fingerprint and amount of each payment stored in the re-read window, so an adapter that values a payment with a request skips unchanged ones, and Stripe keeps a changed charge's share of tax. Stored payments count where they reach the days listed now; after a gap longer than the re-read window, the older ones are read again. `record_revenue_payments` replaces the payments of the windows read completely (a stored payment that a window no longer lists is gone) and returns the totals per currency of each window the stored payments cover, or null for one they do not reach yet; all time needs the first payment. `readRevenue` in `revenue.ts` ties them together and converts to USD.
- **Kinds.** A payment for a subscription counts as one whole, one-time items charged with it included; anything else is a one-time purchase. Each adapter gives the kind of every payment it values, and of unchanged ones where its list shows it, which `record_revenue_payments` stores through `p_kinds`. Payments stored before kinds were read (migration `20261001210000_revenue_by_month.sql`) have none: `revenue_read_state` names the days of those in the charted months (`unsorted`) and gives their stored rows, and once the payments reach the first one, `collectPayments` reads that window again instead of older payments, so each gets its kind without being valued again (Stripe reads their invoice or session, which tells the kind). The recent read gives the kinds of the payments it lists.
- **Months.** Revenue by month covers the same twelve completed months as the MRR history (`revenueMonths`). `record_revenue_payments` returns each month's totals per kind and currency from the first month the stored payments cover in full, payments without a kind under `unknown`, and `revenueHistory` (pure) converts them to USD cents at today's rates: a month whose payments all have a kind gets `subscription_cents` and `one_time_cents`, whose sum is its `cents`; a month with any of unknown kind gets its total only. The months are stored with the snapshot (`revenue_history`), carried over like the other figures, and projected publicly as described under Revenue and discovery.
- **When.** `claim_due_verifications`, which takes over from `claim_due_connections`, also returns whether payments are due: never read, read 23 hours ago, or read an interval ago while they do not reach the first payment yet, so a large account is read back hour by hour. Claiming marks them checked. A new connection reads them right after the founder has the answer (`after()` in `connectProvider`), and a founder's Refresh now reads them when they were not read in the last hour. Any other verification carries over the latest snapshot's figures from the same provider when they were read less than two days ago (`revenueToCarry`). A failed read is written to `revenue_note` and leaves MRR verified.
- **Where.** The product page shows revenue of all time beside MRR in the first row of its card, as Not shared where it is not, and the last 30 days and 12 months in a second row when any figure is shared; its chart switches between MRR and revenue by month. The Markdown version lists the figures and the months, the leaderboard shows all time on every row, and the founder's panel shows the figures with where reading stands (`RevenueFigures` in `revenue-connection.tsx`).

Each provider's payments:

- **Stripe**: charges (`/v1/charges`) that are captured and succeeded, each earning what was captured less refunds and lost disputes (`/v1/disputes?charge=`, for charges marked disputed). A charge that paid an invoice of a subscription (its `parent` or `billing_reason`) paid for it; one that paid any other invoice, a Checkout Session in payment mode, or neither, was a one-time purchase, so a subscription invoice paid more than 35 days after it was created counts as one too. A charge carries no tax, so its untaxed share comes from the invoice it paid (paid invoices created up to 35 days before, with `data.payments` expanded) or the Checkout Session that took it (complete sessions from two days before), 2,000 charges at a time; a charge with neither had no tax that Stripe recorded. This needs Read for Charges, Checkout Sessions and Disputes besides the MRR permissions (`rak_charge_read`, `rak_checkout_session_read` and `rak_dispute_read` in the editor's link, ids that Stripe does not document); without one, the founder is told which.
- **Paddle**: completed transactions by `billed_at`, one-time purchases included, earning the grand total less its tax (credit from earlier transactions is left out), less what adjustments took back, which the transaction's `adjusted_totals` show. A transaction with a `subscription_id` paid for it, unless its `origin` is `subscription_charge`, a one-time charge billed to the subscription.
- **Polar**: paid, partly refunded and refunded orders, one-time purchases included, each earning `net_amount` less `refunded_amount`. An order with a `subscription_id`, or a `billing_reason` of a subscription, paid for one. Lost disputes are not read, since the token has no `disputes:read`.
- **Dodo Payments**: successful payments, a month at a time and each month whole, since the list's order is not documented. The list gives no tax, so each new or changed payment is read alone (`/payments/<id>`): its total without tax, less successful refunds at the same share, and nothing once a dispute is lost. Every request counts against the page limit; a read that runs out covers the days after the newest payment it could not value, and the payments it valued on that day are stored, so the next read goes further even on a day with more payments than one read values. The list names the subscription a payment paid for (`subscription_id`, or `subscription_ids` for several), empty for a one-time payment.
- **Creem**: the whole transaction list, which has no filters, each paid transaction earning what was paid without tax, less refunds at the same share, and nothing when charged back. A transaction of type `invoice`, or with a subscription, paid for one; a `payment` was a one-time purchase.
- **Chargebee**: invoices with a payment (`amount_paid[gt]=0`), one-time charges included, by date: the amount paid at the invoice's untaxed share, so credits and write-offs do not count, less cash refunds from refundable credit notes at their own untaxed share. Invoice ids belong to the site, so a payment's id names the site. A `recurring` invoice paid for a subscription; others are for one-time charges.
- **Whop**: paid payments, one-time purchases included: the total without tax, less refunds without tax, and nothing once a dispute is lost. A payment whose `billing_reason` names a subscription paid for one.
- **RevenueCat**: the daily revenue chart before tax, a year per request back to 2018. Each day counts as one payment of the project, so a day's figure changes as refunds come in. It mixes subscriptions and one-time purchases, so its kind is unknown and its months show totals only.
- **Gumroad**: the sales summary by day (`/v2/sales/summary?group_by=day`), all time in one request: each day's sales in US cents, one-time purchases and memberships alike, after discounts and without the tax Gumroad collects, less refunds. Each day counts as one payment of the account. Its days follow the seller's time zone, and it does not take off lost chargebacks, which a token that can only view sales cannot read. Like RevenueCat's, its days are of unknown kind.

### Connecting Gumroad

Gumroad's personal access tokens hold every scope, so the site asks for `view_sales` alone through OAuth with its own application (`GUMROAD_CLIENT_ID`, `GUMROAD_CLIENT_SECRET`, `gumroad/oauth.ts`). The product form has no key field for Gumroad (`connectsWithOAuth` in `catalog.ts`): saving the form with Gumroad chosen saves the product, and `saveSaas` returns the address `GET /api/gumroad/connect?saas=<id>`, which the browser opens as a plain navigation, since a redirect to another site from a form action would fall under the form-action policy. The route checks that the signed-in founder owns the product, keeps a random state and a PKCE verifier (S256) in a ten-minute, http-only cookie on `/api/gumroad`, and redirects to Gumroad's approval page. Gumroad returns to `GET /api/gumroad/callback` with a code; the callback takes the flow from the cookie and deletes it, requires the same founder, the same state and a product they own, counts the check through `begin_revenue_check`, exchanges the code with the verifier and the application's secret, refuses a token whose scopes go beyond reading sales, and connects it through `connectProvider`, which verifies it before storing it encrypted like any key. That exchange is the one POST sent to a provider, and it changes nothing in the account. The outcome waits for the editor in a one-minute cookie on `/dashboard` (`connection-result.ts`, shared with keys pasted in the form), which the editor shows only with `?connection=1`, so no text from an address reaches the page. Redirects go to `NEXT_PUBLIC_SITE_URL`, the address Gumroad returns to, since Next.js may name the request's host differently and the session cookie would not come along. The adapter's `parseKey` refuses every pasted value.

Connecting is part of the product form, in a Verified revenue section right after the product's details, whose description says it is optional: the founder chooses a provider from a list with each provider's logo (`ProviderLogo` in `src/components/provider-logo.tsx`, brand marks from Simple Icons, Polar's brand kit and the providers' own app icons) and pastes its key, and one save does both. `saveSaas` validates the provider and the key's form first (`chosenConnection` in `src/lib/revenue/connect.ts`), so a key in the wrong form saves nothing, then saves the product, and then counts the check and connects through `connectProvider`. A product is never lost to a key the provider refuses: a new product's editor opens with the outcome from the cookie above and the provider chosen for another key, and an existing product's editor keeps the form as it was and shows the failure at its revenue section, which scrolls into view since the save button is at the end of the form. Success opens the editor with the outcome; with no provider chosen, a new product returns to the dashboard with Product added and an edit with Saved. A connected product shows its figures in the same section, with Refresh now and Disconnect as buttons that call server actions in `src/app/revenue-actions.ts` (the form cannot hold forms of its own), which check ownership on every call since the SaaS id is bound on the client. Before reading an account, every connection, refresh and Gumroad callback calls `begin_revenue_check` (`beginRevenueCheck`), which counts every check, successful or not: a product is refreshed at most once per five minutes (from `last_synced_at` or `last_checked_at`), and a maker starts at most 20 checks an hour (`private.revenue_checks`, kept an hour). Makers see only failures written for them (`VerificationError` in `src/lib/revenue/errors.ts`, which provider request errors extend); anything else, such as a database error, is logged and shown as a generic failure. The product form submits from `onSubmit`, so a failed save keeps the chosen provider, the site or project and the pasted key. `POST /api/revenue/sync`, called with `Authorization: Bearer $CRON_SECRET` (compared in constant time), re-verifies the connections that are due (migration `20260925233000_hourly_verification.sql`). `claim_due_verifications` (which replaced `claim_due_connections`, dropped in migration `20261001200000_drop_first_statistics.sql`), executable by `service_role` alone, claims one at a time for three workers: the connection verified or checked longest ago, once 55 minutes have passed, marking it checked with `for update skip locked` so an overlapping run skips it. A run claims nothing new after four minutes (`maxDuration` is 300 seconds), so the database calls it every ten minutes (see Scheduled jobs); each connection is then verified about every hour. A scheduled verification reads only what MRR needs and carries over the history and 30-day growth from the latest snapshot when the same provider gave them less than 23 hours ago (`history_at`), so the expensive reads happen about once a day; a maker's Refresh now and a new key read everything. `record_revenue_verification` replaces the day's snapshot (UTC) for a re-verification from the same provider instead of adding one, so a product keeps one snapshot per day; a new key always adds one. The projection's trigger runs on updates too. The service-role key (`SUPABASE_SECRET_KEY`) is only read by `src/lib/supabase/admin.ts`, a server-only module used for these trusted writes, the results of domain checks (see Verified domains) and the email worker (see Notification emails).

## Verified domains

Founders prove that they control their product's domain with a DNS TXT record (migration `20260926100000_domain_verification.sql`). Each product has a token in `private.saas_domains`, made by a trigger when the product is created; the record is named `_thesaasharbor.<domain>` and holds `thesaasharbor-verification=<token>`. The domain is the website's host in lowercase and ASCII, without `www.` and a final dot (`websiteDomain` in `src/lib/website-domain.ts`); an IP address or a name without a dot has none, and the editor says so.

- **The founder's check.** The editor's Domain section reads the token through `saas_domain_verification()`, which answers only the founder, and shows the record to add with copy buttons. Check DNS runs `checkDomainAction`, which checks ownership, then calls `begin_domain_check()`: the founder's own product, once every ten seconds per product and 30 times an hour per founder (`private.domain_checks`, kept an hour). The server looks the record up with Node's resolver (three seconds, two tries; long values arrive in chunks and are joined; `DOMAIN_DNS_SERVERS` replaces the system's servers only with servers on this machine, as the browser tests' `fake-site.mjs` is) and stores the result with the service-role client through `record_domain_check()`, executable by `service_role` alone, so a maker can never mark a domain themselves; `verified_domain` and `domain_verified_at` on `saas` have no maker grants. A name that does not exist or has no TXT record is missing; any other DNS failure changes nothing.
- **The daily check.** `POST /api/domains/check`, called every hour by the database with the cron secret, claims verified domains not looked up for 23 hours (`claim_due_domain_checks`, `for update skip locked`), twenty at a time for up to 50 seconds, and records each result. A verified record that is missing starts three days of grace (`missing_since`, which the editor shows); still missing after that, the mark goes.
- **Changes.** A trigger removes the mark as soon as the website moves to another host, however it is written; `www.` does not count as another host. The database reads the host the way browsers do (`private.website_host`: tabs and line breaks are dropped and a backslash counts as a slash), and a website holds no spaces, control characters or backslashes, which the form and a check constraint refuse (migration `20261001090000_website_host.sql`). Before, `https://a.example\@b.example` was `b.example` to the database and `a.example` to browsers, so a mark verified for one could stay on a website on the other. A result for a website that changed during the lookup is dropped. Several products may verify one domain, since the domain's owner can add a record for each.
- **Where it shows.** Verifying is optional. The details box on the product page, under Website, says Domain: Verified or Not verified, and the Markdown versions say the same, with the domain and when it was last checked once it is verified. The page, the Markdown and the editor show the mark only while the verified domain is still the website's domain as browsers read it (`currentVerifiedDomain`), whatever the database has stored. Demo products never have one. The browser tests point the resolver at a DNS server in `tests/e2e/fake-site.mjs` with `DOMAIN_DNS_SERVERS`, which production ignores.

## Deleting data

Makers delete their account under Maker profile → Delete account, confirming with their password. An account whose only sign-in is Google or GitHub (`confirmationMethod` in `src/lib/auth.ts`) has no password to confirm: Confirm with Google (or GitHub) sends it through `/auth/oauth/<provider>?confirm=delete`, which signs in with that provider again for the same account, and the action then calls `deleteSignedInAccount` with the current session, which does steps 2 and 3 below. Otherwise `deleteAccountAction` (`src/app/actions.ts`) calls `deleteAccount` in `src/lib/account.ts`:

1. It signs in again with the password on a separate client without cookies. Auth's rate limit applies, and a wrong password stops here with nothing changed.
2. With that fresh session it removes every file under the maker's folder in `profile-images` through the Storage API, repeating until the folder lists empty. Storage blocks SQL deletes on `storage.objects`, which has no foreign key to `auth.users`, so files would otherwise outlive the account. If this fails, the account stays in place and can be deleted again.
3. It calls `public.delete_account()`. This SECURITY DEFINER function deletes only `auth.uid()`, and only when the JWT's `amr` claim has a password or Google or GitHub (`oauth`) sign-in from the last five minutes, so a leaked or long-lived session token alone cannot delete an account. `private.remove_account` does the deleting, which the cleanup of unfinished sign-ups shares. It deletes the user's audit log entries (email and IP address), leftover refresh tokens and sign-in flows, then the auth user. Foreign keys cascade to the profile, products, settings, provider connections with their keys, subscription claims, snapshots, the public projection, the milestones, the reports the maker sent, the reports and admin decisions about them, their admin rights, the source of the account, their email settings, the emails queued or sent to them, the Telegram alerts about them, and their product additions and revenue checks. The function also deletes other makers' queued emails about the maker's messages and the live-update events that name the maker. Execute is granted to `authenticated` only.
4. The action signs the browser out and redirects to `/account-deleted`.

Makers delete a single product at the bottom of its editor by typing its name. `deleteSaasAction` checks ownership and the name, removes the logo through the Storage API unless the maker's profile photo or another of their products uses the same file, then deletes the row under the `saas_owner_delete` RLS policy. Foreign keys remove the settings, the public projection, the snapshots and the provider connection with its key and claims, which frees the provider account for another product. Referential actions run as the table owner, so makers still cannot write those tables directly. Logos replaced earlier are not tracked and stay until the account is deleted.

The pgTAP suite covers the recent-password requirement, who may delete a product, the complete removal and that other makers are untouched. The browser test covers both flows, including a logo that is also the profile photo and an image seven folders deep, as only files from before migration `20261001170000_owner_images_and_disconnect.sql` can be: account deletion lists the maker's folder at every depth.

Sign-up has two steps in one form (`AuthForm`): the email address and password, which `checkSignupDetails` checks on the server first (Continue), then the username and the Terms of Service box (Create account); `authenticate` checks everything again and creates the account. The Terms box sits in the second step, as on `/auth/finish` after a first sign-in with Google or GitHub, so every way to sign up shows it once, next to the username. The first step stays in the form, hidden, and the form is sent from `onSubmit`, so a refused username keeps the password. Once the account is created, the form gives way to a Check your inbox panel with the address the link went to, which takes the focus. Every auth form starts at the same height: each description fits on one line at the form's width, and the Forgot password link is no taller than a label. Sign-up requires ticking the Terms of Service box, and `authenticate` checks it on the server. It sends the date of the current terms (`termsUpdated` in `src/lib/legal.ts`, which is also their version) as user metadata, and the trigger `private.record_terms_acceptance` copies it into `private.terms_acceptances` with the time when Auth creates the user, so a user cannot change the record later through their own metadata. Only valid dates are recorded, and a missing or impossible one never blocks sign-up. Accounts made through the admin API have no record. The table has a cascading foreign key to `auth.users`, so account deletion removes it (`terms.test.sql`). A future change to the terms can ask existing users to accept the new version and add a row for it.

Profiles come only from sign-up (migration `20261001100000_profiles_from_signup.sql`): the trigger `private.create_profile_from_signup` creates one when the new user's metadata holds a valid username and an accepted Terms version that is a real date no later than today, and `complete_signup` does it afterwards. Users hold no insert privilege on `profiles`, and `save_profile` and `save_saas` refuse an account without a profile (Choose a username first) instead of creating one. Before, a user without a profile could make one with any name, which skipped the username rules (a reserved name such as support became the address) and the Terms. An account created through Google or GitHub arrives without a username or Terms version in its metadata, so the triggers make no profile and record nothing; so does a sign-up made straight through the Auth API without the Terms. `requireUser()` sends every account without a profile to `/auth/finish`, keeping `next`, and every signed-in page and Server Action goes through it, so nothing else opens until sign-up is finished. There `FinishSignupForm` asks for the username and the Terms box, and `finishSignupAction` calls `public.complete_signup(p_username, p_terms_version)`, which creates the profile with the username as name and address and records the accepted version, with the same username rules; it refuses a second call and a future version. The profile keeps nothing from the provider: not the name, the GitHub username or the picture. The daily job `harbor-unfinished-signups` (`private.delete_unfinished_signups`) deletes an account seven days after it was created when its email address is still unconfirmed or it still has no profile, unless it has uploaded images, products or admin rights, which frees its email address and username (migration `20261001150000_unfinished_signups.sql`, `google_sign_in.test.sql`). Before, it deleted only accounts created through a provider without a profile.

The privacy policy is `src/app/privacy/page.tsx`. The operator's name and contact address come from `src/lib/legal.ts`; while the address is unset, the sentences that name it are left out of the policy, the terms, the moderation notices and the decision emails, and they appear once it is set. At the owner's request (2026-09-27) the policy describes how the service handles personal data, in general terms, without promises about how it will work, so it can follow the service as it changes; it keeps what the GDPR asks for: the data, the purposes with their legal bases, who sees it, transfers, how long it is kept and the rights. Anything new that stores personal data must be described there and removed by account deletion, and product-scoped tables need an `on delete cascade` foreign key to `saas`.

## Maker profiles

Profiles are personal and entirely public, and laid out like product pages. `profiles` holds the name, a headline, a location, About (the `bio` column, up to 2,000 characters), links to a website, LinkedIn, GitHub, X and one other site, skills, and the path to the photo. `profile_experience` holds roles with months stored as the first day of the month; a role without an end month is current.

- `save_profile` saves the whole profile and replaces its roles in one transaction. It runs with the maker's rights, so RLS decides and a maker can only write their own profile. It updates the profile that sign-up created and never creates one. A trigger caps a profile at 40 roles however they are written.
- The database repeats the form's rules: skills are at most 20 unique labels of up to 40 characters (checked by `private.valid_labels`), and LinkedIn, GitHub and X links must use https and point to their own site. `profileSchema` in `src/lib/domain.ts` gives the readable messages first.
- The editor (`src/components/profile/profile-form.tsx`) keeps the roles in React state and sends them as JSON. It submits from `onSubmit` rather than the `action` prop, because React resets a form after its action, which would show stale values in controlled fields next to the state that is sent. File fields are cleared after a successful save instead.
- The public page (`src/app/users/[slug]/page.tsx`) follows the product page: a header with the photo, name, @username, headline and location, a row of key figures (products, and verified MRR and paying customers summed over the products that share them, from `makerTotals`), then About, products and experience, with links and skills at the side. Roles are listed current first with LinkedIn-style durations. The owner sees Edit profile and a prompt for missing sections; everyone else sees Send message.

## Messages

Two makers share one conversation (`conversations`, with the participants in a fixed order and a unique pair), created with the first message. Only the two participants can read it, through RLS on `conversations` and `messages`. Everything references `profiles` with `on delete cascade`, so deleting either account deletes the whole conversation, for both makers.

- Writing: `public.send_message(recipient, body)` is the only write path. It is SECURITY DEFINER because makers cannot write these tables, always uses `auth.uid()` as the sender, trims the text (1 to 4,000 characters), requires profiles on both sides, refuses blocked pairs in either direction, and limits each sender to 20 messages a minute, 500 a day and 20 new conversations a day; an advisory lock per sender makes parallel requests count one at a time. A deleted and a suspended recipient get the same answer, so a sender cannot tell a suspension. Errors meant for makers use SQLSTATE P0001; `sendMessageAction` shows those and a generic message for anything else.
- Reading position and read receipts: `conversation_reads` stores how far each maker has read. Both participants read both positions under RLS, which gives read receipts: the sender's newest message says Delivered, and Seen once the other maker has read up to it (`deliveryStatus` in `src/lib/messages.ts`). Nobody else sees them. Makers cannot write the table, so nobody can set their position ahead of what they read or move it back: `mark_conversation_read` (SECURITY DEFINER, the reader is always `auth.uid()`) only moves it forward and never past the newest message, and `send_message` moves the sender's own position to their message. The view `inbox`, `unread_message_count()` and the message emails use it.
- Live updates: a trigger announces each new message with `realtime.send` on the private Realtime channels `user:<recipient>` and `user:<sender>`. The event carries ids only, never the text, and an RLS policy on `realtime.messages` lets a maker join only their own channel. When a maker's read position moves, `mark_conversation_read` sends a `read` event with the conversation id and the position to the other participant's channel, and their open conversation turns Delivered into Seen. `src/components/messages/live.ts` keeps one channel per tab for the header count and the open conversation. The conversation then reads the new message under RLS with the browser client (`src/lib/supabase/browser.ts`), and catches up, reading everything after the newest message on screen and the other maker's read position, once the channel has joined after the page was rendered, when a hidden tab becomes visible again, and when the channel joins again after the connection dropped; the header then counts again too. Writes always go through Server Actions.
- Pages: `src/app/messages/layout.tsx` shows Messages in two panes that fill the window below the header (`MessagesPanes`): the conversation list on the left and `/messages/<maker id>` on the right, with a placeholder at `/messages`. The list stays mounted while conversations open beside it, so only the right pane loads (`loading.tsx`). It is fetched on the server in its own Suspense boundary, then refetched from the view `inbox` with the browser client on new messages, after reading and whenever the channel joins; the open conversation is marked with `aria-current` and shows no unread count. Which conversation is open comes from `useSelectedLayoutSegment()`. Below md only one pane shows: the list at `/messages`, the conversation at `/messages/<maker id>` with a back link. The pages still call `requireUser()`; the layout only reads the current user. The floating Feedback button is left out of Messages, where it would cover the message field.
- The header's unread count is rendered on the server and refreshed on new messages and after reading; the most recently requested count wins. Times are formatted in the visitor's time zone after hydration (`LocalTime`).
- Send message on maker profiles and product pages opens `/messages/<maker id>`. Visitors go to sign-in with `next`, which `safeNext()` limits to the messaging and report pages, so it cannot send anyone to another site.
- A suspended account can neither send nor receive messages (`send_message` checks both sides), and its conversations leave the other maker's inbox and unread count, because both read the other maker's profile under RLS.
- A maker who has not read a new message within five minutes gets one email about the conversation, which names the sender and never contains the text (see Notification emails).

## Reports and moderation

Migration `20260925120000_moderation.sql` adds reports, admin decisions and product limits. The admin panel lives under `/admin`.

- **Admins** are rows in `private.admins`. The app never grants them: `public.set_admin(email, admin)` and `public.list_admins()` are executable by `service_role` only, for `npm run admin` and operators. `public.is_admin()` answers for the caller and is executable by both API roles, because RLS policies call it. Admin functions start with `private.require_admin()`.
- **Visibility.** `saas` rows are public while `hidden_at` is null and the owner's profile is not suspended; `profiles` and `profile_experience` while the profile is not suspended; `public_metrics` exactly when its product is visible (the policy's subquery runs under the `saas` policy). Owners always see their own rows, and admins see every row. Because `public_saas` and `leaderboard` run with the caller's rights, hidden products leave every listing and the ranking without changes to the views. The moderation columns live on `saas` and `profiles`, so the owner reads the reason and explanation from their own row, and nobody else can see a hidden row at all.
- **Reports** are written only by `submit_report(target, id, reason, details)`, a SECURITY DEFINER function. A reporter can report a product or profile that is listed, or a message they received: the message is looked up together with its conversation and the reporter must be one of its two makers, so admins never read a conversation, only the copy of a reported message. Each report stores a copy of what was reported in `content`, so a later edit cannot hide it. Makers cannot report themselves; suspended accounts cannot report; there is one open report per reporter and thing (partial unique indexes); and an account sends at most 10 reports an hour and 30 a day. Illegal content and Something else need an explanation. Reporters read their own reports under RLS (`reporter_id`), admins read all, and the reported maker never sees who reported. `reports` has no column naming the admin who decided, so reporters cannot learn who the admins are.
- **Decisions** go through `admin_hide_saas`, `admin_restore_saas`, `admin_suspend_account`, `admin_restore_account` and `admin_dismiss_report`, all SECURITY DEFINER. Hiding and suspending need a reason from the same list as reports (the `public.moderation_reason` domain, mirrored in `src/lib/moderation.ts`) and an explanation, which the maker sees in their dashboard and editors as a statement of reasons, with how to disagree. Hiding closes the open reports about the product; suspending closes every open report about the maker. Admins cannot suspend themselves or another admin. Every decision is written to `moderation_log` with the admin, the reason, the note and the product or maker name at the time; only admins can read it. The maker is emailed about the decision, and reporters about the outcome (see Notification emails).
- **Admin panel.** `requireAdmin()` in `src/lib/admin.ts` answers a 404 for everyone but admins. It runs in the admin layout and again in every page, because a layout does not guard the segments below it, and every admin Server Action checks `adminSession()`. Pages read through the admin's own session under RLS. The exceptions are account data in `auth.users`, which `admin_accounts(search, filter)` and `admin_account(id)` return after checking admin rights, and revenue figures: snapshots and sharing choices are readable by their founder alone, so `admin_revenue(ids)` (migration `20260928130000_admin_revenue.sql`) returns the latest verified MRR and revenue of the given products after checking admin rights, private figures and hidden products included, with the provider, whether the latest check failed, the founder's sharing choices and whether the figures are more than seven days old and so no longer shown on the site. Like the founder's own dashboard, it counts only products that are connected, and it never returns the key, its hint or the error text. The product list and an account's products show each product's MRR and revenue over the last 30 days (`adminRevenue()` in `src/lib/admin.ts`), and a product's page shows every figure marked Shared or Private. `admin_account` also returns the country of the account's latest sign-in: every sign-in (password, sign-up without confirmation, email link, Google or GitHub) calls `recordSignInCountry()` in `src/lib/supabase/server.ts`, which passes Vercel's `x-vercel-ip-country` header to `record_sign_in_country` with the new session. Only the two-letter code and its time are kept, one row per account in `private.sign_in_countries`, which the account's deletion removes. The user's own session writes it, so like any IP location it is a hint, not proof; locally there is no header and nothing is recorded. Decision forms return to their page with `?done=` and a confirmation; `safeAdminPath()` limits where they may return to.
- **Product limits.** The `saas_limit` trigger allows 20 products per account and 5 new ones a day, however they are written. Additions are counted in `private.saas_additions`, kept a day, which deleting a product does not shorten, so deleting and adding again does not reset the day. An advisory lock per owner makes concurrent inserts wait for each other, so the limits hold exactly. `submit_report` counts a reporter's reports under the same kind of lock. The editor shows the limit before a maker fills in the form.
- **Deletion.** A report is deleted when either the reporter's or the reported maker's account is deleted. Deleting the reported product or message keeps the report and its copy (`on delete set null`), so a maker cannot make a report disappear by deleting the product. `moderation_log` entries are deleted with the account they concern and keep no name once the admin who decided deletes their account. `private.admins` rows go with the account.

- **Feedback.** Signed-in users send bugs, suggestions and other feedback from `/feedback` (migration `20260926050000_feedback.sql`). A button in the corner of every page on screens from 640 px up, and the footer's Send feedback link on all, open it with the page they are on (`FeedbackLink` in `src/components/feedback-button.tsx`), which `feedbackPage()` in `src/lib/feedback.ts` and the database both keep to a path on this site without spaces, control characters or backslashes, so the admin panel never links elsewhere (browsers drop tabs and line breaks from an address, so `/<tab>/x.example` would lead to `x.example`; migration `20261001110000_feedback_page.sql`). The admin panel links a stored page only while it passes the same check. Links inside the site open the form in a dialog over that page (`src/app/@modal/(.)feedback`, `FeedbackDialog` in `src/components/feedback-form.tsx`), in the same slot as the sign-in dialog; a direct visit or reload shows the `/feedback` page. Visitors go to sign-in first (`feedbackLink()`), which continues to the form (`safeNext`): from the sign-in dialog the form opens in a dialog over the same page, and from the full sign-in page as the full page, since `feedbackOpening()` loads the page when Next-Url is under `/auth` and opens nothing over the `/feedback` page itself. `submit_feedback()` checks the kind, 10 to 2,000 characters, suspension and a limit of 5 an hour and 20 a day, and users never read feedback back. Admins read it under RLS on `/admin/feedback` (New, Handled, All) and on the overview, with the day and time it came in in their own time zone (`LocalTime`), and mark it handled or new again with `admin_set_feedback_handled()`. Feedback goes with the sender's account; who handled it is cleared with the admin's account, while when stays.

The privacy policy describes all of this, and the terms at `/terms` list what is not allowed and how decisions and appeals work. Both name the operator from `src/lib/legal.ts`.

## Notification emails

Migration `20260925170000_email_notifications.sql` adds an outbox. Triggers queue each email in `private.email_outbox` in the same transaction as what it is about, so an email is neither lost when sending fails nor queued for something that was rolled back. A row holds the recipient's id, the kind, a topic and ids, never an address or message text.

- **What queues an email.** A new message queues one email per conversation for the recipient, unless they turned message emails off or an email for the conversation was already queued since they last read it. The email is queued at the message's own time, which is also what reading the message records, so the next message after a read always queues a new email; an advisory lock keeps two messages at the same moment from queuing two. A new report queues an email to each admin who wants them, unless one is waiting, due no earlier than an hour after the last one sent. A report that leaves `open` queues the outcome for its reporter. A `moderation_log` entry for hiding or restoring a product, or suspending or restoring an account, queues an email to the maker with the reason, and for hiding and suspending the explanation; notes on reversals are for admins only.
- **Milestones.** A trigger on `public_metrics` calls `private.record_milestones` whenever the public projection changes, which covers verifications and turning MRR sharing on. Only public facts count: MRR that is shared and verified in the last seven days, on a product that is not hidden and whose founder is not suspended. It records each MRR threshold the product has reached ($100, $500, $1K, $2.5K, $5K, $10K, $25K, $50K, $100K, $250K, $500K and $1M; `MRR_MILESTONES` in `src/lib/milestones.ts` lists the same keys) and, once the leaderboard has 25 ranked products, the top 10, top 3 and first place, ranked like the `leaderboard` view. `saas_milestones` has one row per product and milestone, so a milestone is reached once, even after MRR dips and recovers. Everything a verification reaches at once is one email, such as every threshold up to a first verified MRR. Milestones already reached when migration `20260927140000_milestones.sql` ran were recorded without emails. Visitors read milestones only while the product's MRR is verified and shared (an RLS policy on `public_saas`), and product deletion cascades to them.
- **Settings.** `notification_settings` holds whether a maker wants message emails, milestone emails and, for admins, report emails; no row means all. `save_notification_settings` keeps the saved milestone choice when it is called without one. Makers read their own row and write it only through `save_notification_settings`. Decision and outcome emails concern the maker's own content or report, so they are always sent.
- **Claiming.** `claim_emails(limit, message_delay)` and `complete_email(id, status, error)` are executable by `service_role` alone. `claim_emails` takes due rows with `for update skip locked`, locks them for two minutes, and returns the address with what the email needs at that moment (`private.email_context`): current names, the number of unread messages or open reports, and whether the recipient still wants it. A message email is due `MESSAGE_EMAIL_DELAY_SECONDS` (default 300) after it was queued, so makers who are online read the message first. It is skipped at sending when the conversation has been read since it was queued (a later message queued its own email), the two makers blocked each other, or the sender was suspended. A milestone email is skipped when the founder turned milestone emails off or the product's MRR is no longer verified and shared, since its card is then not shown. `complete_email` records the outcome and tries a failed email again after 5, 10, 15 and 20 minutes before giving up. A failure of the service rather than of the email (the server cannot be reached, refuses the site's credentials or answers with a 4xx code, `serviceFailure` in `src/lib/email/failures.ts`) is recorded as `deferred` instead: the email waits five minutes without losing the attempt that claimed it, the run stops, and the log names the failure's code, never its text (migration `20261001130000_outbox_deferral.sql`). Before, every failure counted, so an outage of about 50 minutes, or a revoked key, gave up every email queued meanwhile. `claim_emails` also deletes emails a week after they were processed.
- **Sending.** `deliverEmails` in `src/lib/email/outbox.ts` claims one email at a time, renders it with `templates.ts` (plain text and escaped HTML in the frame from `layout.ts`, which the Auth emails share: the logo, a card with a heading and one button, small print below and a preview line, as tables with inline styles in the light theme's colors; subjects on one line, footers that link to the settings or the terms; a milestone email leads with the best place, then the highest threshold, shows the milestone's sharing card and links to share it on X and LinkedIn) and sends it with nodemailer over one SMTP connection per run. A remote SMTP server must switch to TLS before the password is sent. A run claims nothing new after a minute and every SMTP step gives up after 15 seconds, so an email is never claimed again while it is being sent. Server Actions that queue an email, and the revenue actions after a verification, call `sendQueuedEmails()`, which runs the worker after the response with `after()`. `POST /api/email/send` runs it for up to 100 emails when called with `Authorization: Bearer $CRON_SECRET` (compared in constant time by `src/lib/cron.ts`, like the revenue sync); production calls it every minute, for the delayed message emails, from the database (see Scheduled jobs). Without `SMTP_HOST` and `EMAIL_FROM` the worker claims nothing and emails wait. Addresses and message text are never logged.

## Telegram alerts

Migration `20260928110000_telegram_alerts.sql` tells the owner about new accounts and new feedback in a Telegram chat, through an outbox built like the one for emails. Triggers queue an alert in `private.telegram_alerts` in the same transaction as what it is about: a new account when its profile is created, at sign-up with a username or when a Google or GitHub sign-up is finished, so the alert can name the user; and feedback when it is inserted. An account older than a day that gets its first profile later, such as when it saves a product, is not new, and a partial unique index allows one sign-up alert per account. A row holds only the account's and the feedback's ids, with cascading foreign keys, so alerts go with the account and with the feedback.

- **Claiming.** `claim_telegram_alerts(p_limit)`, for the service role only, locks due alerts for two minutes with `for update skip locked` and returns what each says, read at that moment by `private.telegram_alert_context`: the name and username, and for a new account how it signed up (`app_metadata.provider`), whether the email address is confirmed and the number of accounts; for feedback its kind, text and page. Never an email address. Alerts still pending after a day, such as while Telegram was not configured, are marked skipped rather than sent late, and processed alerts are deleted after a week. `complete_telegram_alert` records the outcome: a failed alert is tried again, five times in all, a minute later per attempt. A failure of Telegram or the setup (Telegram cannot be reached, fails, rate-limits, or refuses the token or the chat; `service` on `TelegramError`) is `deferred` instead: the alert waits a minute, or as long as Telegram asks (`retry_after`), without losing an attempt.
- **Sending.** `deliverTelegramAlerts` in `src/lib/telegram/outbox.ts` claims one alert at a time, renders it with `alerts.ts` (Telegram's HTML, with everything users wrote escaped, and a link to the account or the feedback in the admin panel) and sends it with `api.ts` to the Bot API's `sendMessage`, without link previews. A run claims nothing new after 30 seconds, each request gives up after 10, and a deferred alert, such as after a rate limit, ends the run. Errors keep Telegram's reason, never the token, which is part of the URL. `submitFeedbackAction`, sign-up in `authenticate` and `finishSignupAction` call `sendQueuedTelegramAlerts()`, which runs the worker after the response with `after()`. `POST /api/telegram/send` runs it for up to 100 alerts with `Authorization: Bearer $CRON_SECRET`, and production calls it every minute (see Scheduled jobs). Without `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` the worker claims nothing. The bot only sends; it reads nothing written to it.
- **More kinds.** Migration `20260928120000_more_telegram_alerts.sql` adds alerts for new products (a trigger on `saas`), new reports (on `reports`) and messages (on `messages`) to the accounts in `private.telegram_inboxes`, which the owner sets with `set_telegram_inbox(username, on)` in the SQL editor, as with `set_admin`; the API roles cannot. A message alert is queued once per conversation until the recipient reads it (`conversation_reads`), as the message emails are, comparing the read position with the alerted message's time (migration `20261001120000_message_alert_after_read.sql`; the alert's own time is a moment later, so reading just up to the alerted message used to leave the next message without an alert), and names the sender without the message; it is skipped when the recipient was taken off the list, either user blocked the other or the sender was suspended. A report alert says who reported what and why, with the reporter's explanation, and never the report's copy of a message. A product alert is skipped when the product was hidden. Alerts hold the product's, report's or message's id with a cascading foreign key, and `user_id` is the founder, reporter or sender. `saveSaas` for a new product, `sendMessageAction` and `submitReportAction` send right after the response, like feedback.
- **Tests.** `telegram_alerts.test.sql` covers what queues an alert, what it says, locking, retries, late alerts and deletion, and `telegram_alert_kinds.test.sql` the products, reports and messages; `tests/unit/telegram.test.ts` the messages and the client; the feedback browser test checks the alert that reaches the fake Bot API in `tests/e2e/fake-telegram.mjs`.

## Addresses and sharing

Products live at `/saas/<slug>` and makers at `/users/<slug>` (migration `20260925150000_slugs.sql`); `next.config.ts` redirects the earlier `/makers/...` addresses permanently. Triggers make the slug from the name (lowercase, accents removed with `unaccent`, words joined by hyphens, at most 60 characters) and add `-2`, `-3` and so on when it is taken; makers hold no grant on the column. Saving the same name at the same moment is serialized with an advisory lock. A renamed product keeps its five latest earlier slugs in `private.saas_slug_redirects`, and `saas_slug_redirect()` answers them only while the product is listed. A slug in use always wins over a redirect: a new product may take a slug that only redirects, and the redirect goes, so renaming cannot reserve names for later. A user's slug is their username instead (migration `20260926030000_usernames.sql`): shown as @username under the name and chosen at sign-up, it no longer follows the name. It has 3 to 30 lowercase letters, digits and single hyphens (`usernameSchema` in `domain.ts`, and `private.username_problem` in the database), and a short list of official-looking names is reserved. `check_username()` tells the forms whether a username is free, and `set_username()` changes it; a changed username frees the old one at once, without a redirect, as a renamed maker's slug did. A username can change once every 30 days (`USERNAME_CHANGE_DAYS`): `set_username()` records each change in `private.username_changes`, which is private and goes with the account, and refuses another within 30 days; `username_change_available_at()` tells the profile form, which then shows the field read-only with how many days are left. The username from sign-up, and a profile's first slug, do not count, so the first change is always free. Sign-up sends the username as user metadata, and a trigger on `auth.users` creates the profile with it as both name and slug, so it is reserved at once; if it was taken in the meantime, the slug is made from the name, and without a valid username no profile is made. Profiles made without one (the admin API, older accounts, tests) still get a slug from their name when they are created. Deleting a product or an account frees its slugs.

The proxy answers links with an id, and addresses with capital letters, with a permanent 308 redirect before rendering; it looks up only id-shaped addresses, as a visitor would. A product named like an id keeps its address: a slug that equals the address wins over an id, and the proxy never redirects an address to itself, which looped for a product named after its own id. An earlier product slug redirects from the page itself (`findSaas` in `src/lib/data.ts`), also with a 308, since public pages are not streamed. Private areas, such as messages, reports and the admin panel, keep using ids.

`metadataBase` comes from `NEXT_PUBLIC_SITE_URL` (`src/lib/seo.ts`), so canonical links, the sitemap and sharing images use the public origin. Every public page sets its title, description, canonical address and Open Graph and Twitter card metadata through `pageMetadata()`. The leaderboard, Browse and New arrivals use `listMetadata()`: a search is `noindex, follow`, a category or technology filter points at the plain list, and a later page (`?page=2`) is a canonical page of its own with the number in its title, as Google advises for lists split into pages; a page past the last one answers 404 (`Explore`). Links that change one choice of a list, such as Show all technologies and Clear filters, keep the others, the ranking included. The home page adds the site's name to its own title, since the root layout's title template covers only the pages below it. The root layout allows large image previews and snippets of any length (`max-image-preview:large, max-snippet:-1`); a page with its own `robots`, such as a `noindex`, replaces that. A profile's description is its headline, or else the start of its About section, followed by the products the user is the founder of (`profileDescription`). A profile without products, a headline and an About section is `noindex`, like the sitemap, which leaves out profiles without products. Each revenue ranking (`/?by=30d`, `12m`, `all`) is a page of its own with its own title and canonical address, and answers with `noindex`, and stays out of the sitemap, while no product has revenue for its window (`revenueRankedCounts`: the windows can differ, since a product whose payments are not read back to the first has no all-time figure yet). The statistics page does the same while fewer than five products share verified MRR. `opengraph-image.tsx` for products, makers and the site draws a 1200 × 630 card with `next/og` in the Geist it bundles (`src/components/og-card.tsx`): name, tagline or headline, logo or photo (PNG and JPEG; WebP shows initials, as Satori cannot draw it), and only the figures the page shows publicly. The site's own card (`siteImage`), also used when a product or maker card has nothing to show, invites founders of small SaaS: free exposure, free to list, made for indie SaaS, and the four providers; it holds no live figures, so it is drawn once rather than per request. The badge at `/saas/<slug>/badge.svg` (`src/lib/badge.ts`, served by a route handler) is an SVG makers embed on their own sites, linked to the product page. It shows the product's MRR only while `public_saas` has it as `verified`, and otherwise says Listed on The SaaS Harbor; it holds no text a maker wrote. `?theme=dark` gives the dark colors, which repeat the surface tokens, since an image on another site cannot read `globals.css`. Text is measured with Helvetica widths and drawn with `textLength`, so a fallback font keeps the layout. An id, an earlier slug or capital letters redirect to the current badge, and hidden products and unknown slugs answer 404. The proxy's matcher leaves the path out, so the route sets its own headers: `Cache-Control: public, max-age=600`, `Content-Security-Policy: default-src 'none'`, `Cross-Origin-Resource-Policy: cross-origin` and `X-Robots-Tag: noindex`. The product editor previews it and gives the HTML and Markdown to paste (`src/components/badge-embed.tsx`). A milestone has its own page at `/saas/<slug>/milestones/<key>` (such as `mrr-10000` or `top-3`), which the milestone email links to: the milestone, when it was reached, the provider, the product, links that open a post on X or LinkedIn, the image to download and the address to copy. Its `opengraph-image.tsx` draws the milestone on the same card, so a post with the link shows it. The page and the card exist only while `saas_milestones` shows the milestone to visitors, that is while the MRR is verified and shared; otherwise the page redirects (307) to the product page, since the milestone may be shown again. An unknown key is a 404, and an id or an earlier slug moves to the current address with a 308. The page is `noindex, follow` and not in the sitemap, as the product page is the one for search results. `sitemap.xml` lists the static pages, the revenue rankings once a product shares revenue, every listed product and the makers behind them, read as a visitor a thousand at a time (the API's row limit), so hidden products and suspended makers never appear; `robots.txt` keeps crawlers out of the dashboard, admin panel, messages, reports, sign-in and the API.

## Search engines and AI assistants

- **Category pages.** `/categories` lists the categories with their counts, and `/categories/<slug>` (the name in lowercase with hyphens, `categorySlug` in `domain.ts`) shows the category's ranked products as a leaderboard, then its other products A to Z, one page each with a link to the full list. Demo products are left out, since these pages are meant for search engines. The counts come from the `category_counts` view (migration `20260925210000_category_counts.sql`), which groups `public_saas` with the caller's rights, so hidden products and suspended makers never count. A category without listed products answers with `noindex` and is left out of the sitemap. Product pages link to their category page, and the footer to `/categories`.
- **Technology pages.** Founders tick the technologies a product is built with (at most 20) from the catalog in `src/lib/tech.ts`, grouped into Frontend, Mobile and desktop, No-code, Backend, Databases, Hosting and infrastructure, Payments, AI and Services (migration `20260926090000_tech_stack.sql`). `saas.tech_stack` stores the slugs; the database checks their form, count and uniqueness (`private.valid_tech_stack`, which makers and the server may execute, since a check constraint runs with the rights of whoever writes the row), and `saasSchema` checks that each is in the catalog. A slug that later leaves the catalog is ignored wherever a stack is shown. The product page shows the stack as a closed card (`<details>`, `src/components/tech-stack.tsx`) whose one line names the technologies, and which opens to list them by group, each linking to `/tech/<slug>` (the links stay in the page for crawlers while it is closed). `/tech/<slug>` lists the products built with it like a category page: ranked ones first, then the rest A to Z, one page each, with links to the leaderboard and Browse filtered by `?tech=`. `/tech` lists every technology with its count from the `tech_counts` view, which groups `public_saas` with the caller's rights like `category_counts`. Demo products name no stack, so they never appear there, and a technology filter leaves them out. Technologies without products answer with `noindex` and stay out of the sitemap; the Markdown versions and llms.txt list the stack and the technologies in use. The editor shows the catalog as a checkbox per technology in groups that open when something in them is ticked; `useEditorAction` keeps every value of a checkbox group, one per line, so a failed save shows what was sent. The product form submits from `onSubmit`, like the profile editor, so React does not reset it after a failed save, which would clear a chosen logo and the remove box.
- **Complete pages.** Crawlers such as GPTBot, ClaudeBot and PerplexityBot read the HTML without running JavaScript, and text extractors often drop hidden elements. Public pages therefore have no `loading.tsx` above them: the server sends the page once its data is there, with the content in `<main>` rather than in hidden blocks behind a placeholder, and a missing product, profile, category or technology answers 404 instead of 200 with `noindex` (Next.js can set the status only before streaming starts). The HTML of such a 404 is Next.js's bare error document, and the browser draws the not-found page once the scripts load; the theme script is in its head all the same, and the theme menu re-applies a saved theme after React draws the page. `htmlLimitedBots: /.*/` in `next.config.ts` makes the metadata blocking for every user agent, so the title, description and canonical link are in the head, where Next.js would otherwise stream them into the body for all but a list of known bots. Nothing waits longer for it, as the page waits for the same cached loaders. Private areas keep their placeholder, since crawlers stay out of them.
- **Structured data.** `src/lib/structured-data.ts` builds schema.org JSON-LD, which `src/components/json-ld.tsx` renders with the request's nonce: on the home page an `Organization` with its logo (`/logo.png`) and a `WebSite` published by it, joined in one `@graph`, and the first page of each ranking, by MRR at `/` and by revenue at its `?by=` address, as a `CollectionPage` with an `ItemList` when it is not searched or filtered; a `WebPage` with a `SoftwareApplication` and breadcrumbs on product pages, `ProfilePage` with a `Person` on maker pages, and `CollectionPage` with an `ItemList` on the category and technology pages. Each page points at the site's `WebSite` with `isPartOf`. It repeats only what the page shows, never demo products, and `<` is escaped so the data cannot close its element.
- **Icons.** Every page links two icons. `icon.tsx` draws a 192-pixel PNG for search results, since Google's favicon guidelines list no SVG, and `icon1.svg` is the favicon browsers choose, as it follows the color scheme. Next.js links numbered icons in name order, so the PNG comes first. `/favicon.ico` is a route that draws the logo into an ICO file with PNG images of 16, 32 and 48 pixels when the site is built (`src/lib/ico.ts`), since Next.js only serves a favicon file and cannot generate one; services that ask for `/favicon.ico` instead of reading the icon links get it. `apple-icon.tsx` draws the Apple touch icon on the light page color, as iOS fills clear pixels black, and `/logo.png` is the organization's 512-pixel logo. The PNG icon, the ICO file, the Apple touch icon and the logo come from `src/lib/logo.ts` through `markImage` in `og-card.tsx`, and the proxy's matcher leaves every icon and the logo out.
- **One host.** In production, `next.config.ts` redirects every host but the one in `NEXT_PUBLIC_SITE_URL`, such as the project's `vercel.app` address, to that origin with a 308, so search engines find one copy of the site. `/api/` is left out, so the scheduled jobs work whatever address they call.
- **IndexNow.** Production tells Bing, Yandex, Seznam, Naver and the other search engines that take part in IndexNow (indexnow.org) about a product page when its founder saves or deletes it (`src/lib/indexnow.ts`), after the response with `after()`. A product is announced at most once an hour: the save asks `claim_index_notice` through the founder's session, which keeps the time in `private.index_notices` (migration `20261001180000_index_notices.sql`), so saving again and again, or a script, cannot flood the engines. A saved product is read as a visitor would read it, so a hidden product or one whose founder is suspended is never announced; a renamed product's earlier address is announced too, since it now redirects. Only public product addresses are sent. The key is public by design and served at `/indexnow.txt`, where the engines check it. A failure is logged and changes nothing else; the sitemap still lists the page. Bing's index also serves ChatGPT search, Copilot and DuckDuckGo.
- **Pages for founders choosing where to list.** `/list-your-saas` answers what search engines and AI assistants are asked about listing a new SaaS: what a listing gives, how the site differs from other directories, the steps and the common questions. It states only how the site works today (the product limits come from `moderation.ts`), and its questions are also `FAQPage` data (`faqJsonLd`), built from the same list so the two cannot drift apart. `/where-to-launch` is a guide to other places founders launch a SaaS, from `src/lib/launch-guide.ts`, with the date it was checked (`GUIDE_CHECKED`) and links to each site's own pages; its `Article` data names the places. When a site changes its terms, update the entry and move the date. `SITE_DESCRIPTION` and llms.txt say the same: listing is free, public at once without a review queue, open to products without revenue, and the leaderboard has no paid placements.
- **Titles.** A product's title and description carry a figure its page shares only when it is above zero (`productSummary` in `src/lib/seo.ts`): verified MRR, such as "QueryBird: $4,200 verified MRR", with the paying customers in the description, or else revenue from all payments, such as "QueryBird: $1,500 verified revenue", for products sold once. Shared revenue also goes into the description beside MRR. The tagline ends as a sentence before the figures, and a product with nothing to show has its name and tagline.
- **llms.txt and Markdown.** `/llms.txt` (llmstxt.org) describes the site, how revenue is verified, that listing is free and where founders sign up, the rankings by MRR and by revenue, the categories with their counts and the top 50 of the leaderboard. Every product and maker page has a Markdown version at its address with `.md` added: the proxy rewrites `/saas/<slug>.md` and `/users/<slug>.md` to route handlers under `/md/`, which answer ids, earlier slugs and capital letters with a redirect to the current `.md` address, like the pages. Pages announce their Markdown version with `<link rel="alternate" type="text/markdown">`. `src/lib/markdown.ts` writes them with exactly what the HTML pages show; text makers wrote is escaped so it cannot add headings, links, code (tilde fences included) or other structure, every figure the HTML page shows reads not shared where it is missing, and each file and llms.txt say which parts makers wrote and that they are not instructions. They answer with `X-Robots-Tag: noindex` and a canonical `Link` to the HTML page, and `robots.txt` keeps crawlers out of `/md/`.

## Statistics

`/stats` adds up the leaderboard's figures. `public.directory_stats()` (migration `20260925220000_directory_stats.sql`) computes them in one query and returns JSON: the number of ranked products, combined and median MRR, paying customers summed over the products that share them, five MRR buckets (always all five), each category's count, combined and median MRR, the 30-day change (median and how many grow, shrink or stay), four bands of time since launch from shared launch dates, the month-end history summed over the ranked products for the months every one of them covers, and the five fastest growing products with at least $1,000 MRR. It is `security invoker` and reads `leaderboard`, so only shared, fresh, verified figures of listed products count, the same figures the leaderboard shows one by one; demo products never do. `parseStats` in `src/lib/stats.ts` validates the result, so a malformed answer fails instead of showing a wrong figure. Below five ranked products (`STATS_MINIMUM`) the page and its sharing card show no figures. The distributions are bar lists (`charts/bar-list.tsx`) in `--chart-1` with the value in text at each bar's end, and the history reuses the product page's chart with its table view.

## Site statistics

Visits are counted twice, both without cookies or storage on the device.

**Collecting.** `PageViews` (`src/components/page-views.tsx`, in the root layout) posts to `POST /api/analytics`: each page the browser shows, how long that page was visible, and clicks on links to other sites. A page view carries its path and query, a random key the page makes for it (`crypto.randomUUID`), the tab's `document.referrer` and, after the first page, the tab's first address, which count only if the page starts a visit (after 30 idle minutes, or when the daily visitor hash changed), so such a visit keeps where the tab came from instead of counting as direct. It also carries the page before's visible time by its key, so that time counts before the visit is decided, and system hints: `platformVersion` from `navigator.userAgentData` where the browser has client hints (Chromium), and whether a Mac user agent has a touch screen, which only an iPad asking for desktop pages has. Visible time starts when the loaded page was first shown (the navigation's start, a prerendered page's activation or the last `visibility-state` entry), not when React hydrates, and is sent by the page's key when the page is hidden or left, and with the next page view. Query changes on the same path, such as filters, are not new pages. A dialog opened by an address, such as sign-in, is a page of its own; `RouteDialog` says where it was shown, and closing it continues the view of the page beneath rather than counting that page again. Admin pages and automated browsers (`navigator.webdriver`) send nothing. The route refuses other origins (`Origin` must match `Host`, and `Sec-Fetch-Site` must be same-origin where sent) and bodies over 4 KB, and leaves out bots, scripts and headless browsers (Next.js's `userAgent().isBot` and `isAutomated` in `src/lib/analytics.ts`) and signed-in admins. `pageView` keeps the path without its query, replaces ids with `[id]` so private addresses point at no one, and keeps the five `utm_*` tags; `referrerHost` keeps only another site's host, without www, or `android-app:<package>` for a link opened from an Android app, which gives `android-app://<package>/` as the referrer; `outboundTarget` keeps a clicked link without query or fragment. Country and city come from Vercel's `x-vercel-ip-country` and `x-vercel-ip-city` headers (none locally), the language from `Accept-Language`, and device, browser and system with their major versions from `technology` in `src/lib/analytics.ts`. It reads the user agent through Next.js's `userAgent()` but leaves a system version unknown where browsers freeze it: Android 10 with model K (Chrome and Samsung Internet), Windows NT 10.0 (Windows 10 and 11), macOS 10.15 (every Mac browser) and, since iOS 26, iOS 18.6 or 18.7 outside Safari. Safari on iOS gets the system version from its own version, since it ships with the system. Client hints then give Android, macOS and Windows versions (13 and up is Windows 11), only when their platform matches the user agent's system. An iPad presenting itself as a Mac counts as an iOS tablet. In-app browsers get the app's name (Google app, X app, Reddit app and others, or iOS or Android in-app browser) and no version. The route writes through `track_page_view`, `track_page_time` (migration `20260927120000_analytics_precision.sql`) and `track_outbound_click` (migration `20260926070000_analytics_reports.sql`) with the service-role client, since visitors have no session and nothing a visitor sends is trusted beyond these cleaned values.

**Storing.** `private.analytics_visitor` hashes the IP address and user agent with a random salt for the UTC day (`private.analytics_salts`, deleted when the day is over) into a 16-byte visitor, and neither is stored. A page view continues its visitor's visit (`visit`, the id of the visit's first page view) while the visitor was active in the last 30 minutes, by a page view or by a page's visible time after it (`created_at` plus `engaged_ms`); only a visit's first page keeps the referrer and campaign tags. Page time comes by the page view's `key`, which only the page knows, so it is accepted from any address (after a change of network or the daily hash) for a day; it never shortens and is at most an hour. A key already taken is not stored twice, and the retention job clears keys older than a day. The earlier `track_engagement`, by id from the same visitor, stays for the code that was live while the migration was applied. A visitor records at most 300 page views and 100 link clicks an hour. Page views and link clicks live in `private.page_views` and `private.outbound_clicks`, out of reach of the API roles, and are kept 25 months, enough to compare a year with the one before; the pg_cron job `harbor-analytics-retention` deletes older ones and past salts daily. They are not linked to accounts, so account deletion does not touch them.

**Reports.** Admins read totals only, one report per card, through `admin_analytics_overview`, `_breakdown`, `_heatmap`, `_behavior`, `_live`, `_platform` and `_funnel`, which check admin rights and return JSON. `private.analytics_period` turns a period and the viewer's time zone into whole local buckets up to now: 24 hours by hour, 7 or 30 days by day, 12 months by week, and all time from the first page view by hour, day, week or month to fit its length; each but all time has the period of the same length before it, aligned to the same buckets, for the changes and the dashed line. `private.analytics_views` gives each page view its time on the page: the reported time, else the time until the next page of the visit (at most 30 minutes), else unknown. `private.analytics_visits` groups them into visits with their duration (the sum of the known times, unknown when none is known, so averages leave such visits out and the behavior report counts them as Length unknown), whether they bounced (one page), and where they came from and on what, from the visit's first page view: its channel (`private.analytics_channel`: paid, email, AI assistants, organic search, organic social, referral or direct, campaign tags first) and source name (`private.analytics_source`, such as Google or Hacker News). Both read a known Android app as its site through `private.analytics_referrer_site` (the Reddit app as reddit.com), so the mapping also applies to earlier visits; other apps are referrals named by their package. Google search is google.<tld> itself, and Google's other sites, such as docs.google.com, are referrals. Breakdowns of pages count page views and time on page, entry pages and every visit attribute count visits, bounce rate and visit length, exit pages count exits and the exit rate, and links count clicks; a breakdown returns its top 10 or 100 rows and how many there are. The panel shows the change of a rate (bounce rate, sign-ups per 100 visitors) in percentage points (`pointChange`) and of every other figure in percent. The platform report counts sign-ups, products, provider connections, messages, reports and feedback in the period, and totals now; deleted accounts and products are gone from it. Its ranked products and their MRR come from `private.ranked_saas()`, the leaderboard as visitors see it (not hidden, the founder not suspended, MRR shared and verified in the last seven days): the reports run as their owner, whom RLS does not limit, so reading `public.leaderboard` there counted hidden products too (migration `20260927150000_funnel.sql`). The funnel report (`admin_analytics_funnel`, same migration) follows the accounts created in the period, not events in it: how many confirmed their email, listed a product (the first one they still have), verified revenue (a snapshot of a product they still have) and have a product on the leaderboard now. Each step counts only the accounts that took every step before it, so the funnel always narrows, and gives the median time from sign-up where there is a time to measure; the leaderboard has none, since it is a state rather than an event. It also returns the visitors of the period, and the same figures for the period before. `funnelRows` in `src/lib/analytics-reports.ts` turns them into the share of sign-ups (with its change in percentage points), the share of the step before, and the step that kept the smallest share, which the card names as the largest drop. Migration `20260927160000_account_sources.sql` moves the funnel's accounts into `private.funnel_cohort`, one row per account with the steps it took and its last one, which the steps, the lists and the sources share.

**Stopped here.** Each step of the Funnel card links (`stoppedHref`) to `/admin/accounts?stopped=<step>&range=<range>&tz=<zone>`, the accounts of the same period whose last step it is (`admin_funnel_accounts`, in the same shape as `admin_accounts`, so the page lists them the same way). The page offers a mailto link with every address in blind copy, while it fits the 2,000 characters email programs accept, and a button that copies them all (`EmailAccounts`), so admins write to them from their own email program; the site sends nothing itself.

**Where accounts come from.** A new account keeps the source of the visit that led to it in `private.account_sources`: the entry page view's referrer, campaign tags and path. Not when the visit began: that time was the entry page view's own, to the microsecond, and found the account's visits in the statistics, which are kept apart from accounts (migration `20261001160000_account_source_visit_time.sql`). `recordAccountSource` (`src/lib/account-source.ts`) calls `record_account_source`, executable by `service_role` alone, with the request's IP address and user agent when email sign-up creates the account (`authenticate`) and when a sign-in through Google or GitHub returns with an account made in the last hour (`/auth/callback`). The database turns them into the day's visitor hash, as `track_page_view` does, and takes the visitor's latest visit today that came from somewhere (a referrer or a campaign tag), else the latest visit; neither the address nor the hash is stored with the account. An account gets a source once, within an hour of its creation, and none when no visit matches: automated browsers and signed-in admins are not counted, and a visit from an earlier UTC day has another hash. The source is kept with the account and deleted with it. `admin_analytics_sources` groups a period's funnel by channel, source, campaign or first page (`private.funnel_sources`, reading the channel and source with the same functions as the site statistics), with accounts without a source as one row, for the card Where accounts come from; an account's page in the admin panel shows its source under Came from. The queries read the rows of the period; if traffic grows far beyond a small site's, daily rollups would keep them fast.

**The page.** `/admin/analytics` renders `AnalyticsDashboard` (`src/components/admin/analytics`), which reads each card's report from `GET /admin/analytics/data` (`adminSession()` or a 404, the request validated by `reportRequestSchema` and the answer by the report's schema in `src/lib/analytics-reports.ts`) in the browser, with the browser's time zone. Changing a card's period, a tab or the rows shown fetches that card's report alone: buttons, not links, so the page neither reloads nor scrolls, and the last report stays in view, dimmed, until the new one arrives (`useReport`, which also keeps a minute's cache per report). The row above the cards sets every card's period at once; the periods are remembered in the admin's browser. The live card reads again every 30 seconds while the page is visible. The time chart (`time-chart.tsx`) draws the period as an area in `--chart-1` and the period before as a dashed `--chart-muted` line, with a legend, a crosshair tooltip, arrow keys and a table view; the weekday and hour map uses `--chart-1` in five steps; breakdowns are tables with a tint behind each label for its share of visitors, and their secondary columns show from 640 px.

**Product page views.** A product's page shows its founder how often it was viewed (migration `20260926080000_product_page_views.sql`). When `track_page_view` records a view of `/saas/<slug>` whose product is listed (not hidden, its owner not suspended), it also adds one to that product's row for the UTC day in `private.saas_page_views` (product, day, views). The analytics route passes the signed-in user's id (`p_viewer`), looked up once per beacon since React's `cache` does not reach Route Handlers, and a founder's views of their own product do not count; the id is not stored. Earlier slugs are not matched, since their pages redirect to the current one. The counts hold no visitor data, have an `on delete cascade` key to `saas`, so they go with the product and the account, and are not touched by the 25-month retention, so all-time totals keep growing. `saas_page_view_counts(p_saas)` returns the last 7 and 30 UTC days (today included) and all time, and raises 42501 for anyone but the founder. `/saas/[slug]` calls it only when the viewer owns the product, and `ProductProfile` shows the three figures in a Page views card at the top of the side column; a failed read leaves the card out.

**Vercel Web Analytics.** In production the root layout also renders Vercel Web Analytics (`src/components/vercel-analytics.tsx`, `@vercel/analytics`) when `VERCEL_ENV` is `production`; elsewhere nothing is loaded. Vercel serves its script and receives page views on the site's own origin (`/_vercel/insights/*`), and the script is added by a nonce-carrying bundle, so the Content Security Policy needs no change. It counts visitors by a hash that changes daily. Before anything is sent, `vercelEvent` in `src/lib/analytics.ts` drops admin pages and every query value except the `utm_*` campaign tags, since addresses such as `/auth/confirm` carry tokens. The same component renders Vercel Speed Insights (`@vercel/speed-insights`), which reports Core Web Vitals per page from `/_vercel/speed-insights/*` on the site's origin, with the same `vercelEvent` cleaning. The figures of both are read in the Vercel dashboard.

The privacy policy describes it in general terms under Site statistics.

## Security headers

Session cookies carry `Secure` whenever `NEXT_PUBLIC_SITE_URL` is https (`cookieOptions` in `src/lib/supabase/config.ts`, used by the server, the proxy and the browser client). The proxy's permanent redirects from an id to a slug are not cached, since a maker's slug follows their name. `src/proxy.ts` sets a Content Security Policy on every response, built by `src/lib/csp.ts` with a fresh 128-bit nonce per request. Scripts run only with that nonce (`'strict-dynamic'` lets them load their own chunks); Next.js reads the nonce from the request's policy and puts it on its framework scripts, and the root layout reads `x-nonce` and passes it to the inline theme script. `'unsafe-eval'` is allowed only in development, where React needs it. Styles allow inline use, because React writes `style` attributes, which a nonce cannot cover. Images may come from Supabase Storage, and the browser may connect to Supabase and its Realtime websocket; nothing else is allowed from other origins. Framing, plugins, foreign form targets and `<base>` changes are refused, and requests are upgraded to https when the site is served over https. A nonce requires dynamic rendering, which every route already uses. `next.config.ts` adds `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, and in production `Strict-Transport-Security` (two years, without subdomains, which may belong to other services). The browser tests fail on any console report of a blocked resource, and check that each response has a new nonce. `global-error.tsx` has no inline script, because a client component cannot read the nonce; its theme follows the operating system.

## Interface

On the site people are users, and a user is the founder of the products they own: product pages, cards, sharing cards and the Markdown call the owner founder, and everything else says user or profile. Code, the database and these documents keep the older word maker for the same person.

Styling uses Tailwind utilities in the components. Design tokens (colors, fonts, radii) live as CSS variables in `src/app/globals.css` and map to Tailwind names such as `bg-muted`, `text-muted-foreground` and `text-brand`. There is no page-specific global CSS. The type is Geist, loaded with `next/font`, and body text is never smaller than 12 px. The palette is neutral with one teal accent (`--accent`) for links, focus rings and checkboxes, and separate `--logo-*` tokens for the logo. The logo is a lighthouse above a rising bar chart and the sea, drawn once in `src/lib/logo.ts`: the header, footer and sign-in pages render it with the tokens (`src/components/logo.tsx`), and the favicon (`src/app/icon1.svg`, which follows the browser's color scheme), sharing images and badge use the same colors from `LOGO_COLORS`. A unit test keeps those colors equal to the tokens and `icon1.svg` equal to the generated mark; `npx vitest run -u` rewrites the favicon after the logo changes. Cards, tables and fields sit on `bg-surface`, one step lighter than the page background, and are raised by one of five shadow tokens: `shadow-control` for fields, outline buttons and option cards, `shadow-button` for primary buttons, `shadow-card` for cards, tables and panels, `shadow-raised` for a hovered link card, and `shadow-float` for menus and the feedback button. The light theme's shadows are tinted with the logo's navy; in the dark theme raised surfaces also catch a faint light edge on top, since shadows barely show on navy. `cn()` (`src/lib/utils.ts`) tells tailwind-merge these names, which it would otherwise read as shadow colors. Primary buttons use the foreground color. Destructive buttons use `--destructive` with `--destructive-foreground`, which is dark in the dark theme because white text on the lighter red there fails contrast.

There are two themes, light (warm paper, dimmed so it never glares, `#e8e6df`) and dark (the deep navy of the logo, `#0e1520`), and neither is pure white or black. `globals.css` defines each token once for light and once inside `@variant dark`. The custom `dark` variant matches `data-theme="dark"` on `<html>`, or the OS dark preference when light was not chosen, so "System" needs no JavaScript. The choice is stored in a `theme` cookie by the theme menu (`src/components/theme-menu.tsx`). A small inline script from `src/lib/theme.ts` runs in `<head>` before first paint and sets `data-theme` from the cookie, following the Next.js guide on preventing flash before hydration. `ThemeScript` (`src/components/theme-script.tsx`) puts it into the server's HTML with `useServerInsertedHTML`, so it is never a React element: React does not run a script it creates in the browser and warns about one, which it would do on every 404, where it draws the root layout itself. The browser tests check that the script is in the head of a page and of a 404, and that React never warns about a script. The server never reads the cookie, so the theme does not stop pages from being cached later. `color-scheme` follows the theme, so native controls such as the date picker and scrollbars match. Components should rarely need `dark:` utilities, because the tokens switch instead.

The home page has one decorative element, the logo's light (`src/components/lighthouse-beam.tsx`): a soft wedge of the `--beam` color that starts at the lantern of the logo in the header and crosses the top of the page behind the content. It is positioned against the page rather than its section, so it lines up with the header's logo at every width, and no ancestor of it may be positioned. It is plain CSS, a conic gradient faded along its length by a radial mask and animated only through `opacity` and `rotate` (`animate-beam` in `globals.css`), so it needs no JavaScript and runs on the compositor: it fades in once and then sweeps 9 degrees either way, 12 seconds each way. With reduced motion it stays still. The leaderboard's sparklines draw themselves once in the same way, row after row, with their end dot last (`animate-draw` and `animate-dot-in`); reduced motion shows them drawn. The header has no background of its own and scrolls away with the page rather than staying on top, so the light shows from the lantern on and nothing cuts it off.

Shared building blocks live in `src/components`: `site-chrome.tsx` (header, and the footer with its links in three groups), `account-menu.tsx` (the signed-in user's photo and name at the top right of the header, a menu with their profile and account pages and Sign out, filled once per request by `accountMenu()` in `src/lib/account-menu.ts`), `shell.tsx` (page width, page header, notices, empty states), `listings.tsx` (leaderboard, product cards, pagination), `product-profile.tsx` (the product page, for real and demo products: one card with the name, status labels, the website and message buttons and the key figures), `avatars.tsx` (rounded-square product logos, round person avatars), `forms.tsx` (settings-style form sections) and `charts/` (revenue charts).

Charts follow one set of rules. `src/lib/charts.ts` builds chart models on the server (the zero-based axis with round steps, month names, whole-dollar labels), so client code never formats numbers. The product page and `/stats` show MRR at month end as an area chart (`charts/revenue-history.tsx` with `charts/history-chart.tsx`): the latest month-end figure large at the top with its change over the period, which shows the month under the pointer or the arrow keys instead, a choice of 3 months, 6 months, a year or all (`chartPeriods`), and an area that fades downwards under a line that draws itself again for each period. Where revenue by month is shared, the product page's card has tabs (a tab list with arrow keys) for MRR and Revenue, and the period chosen carries over to the other tab where it offers it. Revenue by month is a column per month (`revenueChartModel`), at most 24 px wide with a 2 px gap between its parts: subscriptions in `--chart-1` below, one-time purchases in `--chart-2` above, the top end rounded, and the columns rising once per period. Its figure is the period's total, or the month under the pointer, whose column stays full while the others dim, and a legend under it gives each part's amount. The split shows only when every month of the history has one, so the parts read the same across the periods. The server makes every period's model and caption, so the client component only switches between them, draws the crosshair or dims columns and reads months aloud; it is laid out in percentages so it renders on the server at any width without measuring. On narrow screens the axis names every other month, or every third in a history longer than six months, so labels with a year never touch. A table of the whole history sits under each chart. Leaderboard rows show a 12-month sparkline (muted line, latest month in the accent; its range spans at least 30% of the peak so small wobbles stay small) of MRR, or of revenue by month in the revenue rankings, and the 30-day growth, whose direction is carried by an arrow and a sign as well as by color. Chart colors are the `--chart-1` (teal), `--chart-2` (the amber of the logo's light) and `--chart-muted` tokens, checked in both themes with the dataviz palette validator for lightness, chroma, at least 3:1 contrast on the surface and, as a pair, separation under protanopia and deuteranopia. Copy is plain and specific, without metaphors. Product logos next to a visible name are decorative (`alt=""`); the maker page avatar carries the maker's name.

## Images and forms

The server validates PNG/JPEG/WebP signatures, the 2 MB limit and a size of at most 4096 pixels on each side (read from the header by `src/lib/image-format.ts`, since a small file can unpack to a huge picture) before uploading an immutable random filename under the authenticated user's prefix. SVG is excluded. A check constraint limits stored image paths to a file directly in the owner's folder with an image extension, and the Storage insert policy does the same for uploads, so no file lands in a subfolder (migration `20261001170000_owner_images_and_disconnect.sql`). Makers can still upload to their own folder straight through the Storage API, which checks only the declared type and size, so the signature and size checks apply to uploads through the app. Storage enforces the matching MIME/size and ownership policies. Failed database saves remove their newly uploaded file. Replacing or removing a displayed image leaves previous uploads in storage in this first version; a future referenced-file cleanup job can remove them safely.

Validation runs on the server. A field's hint is its control's description (`aria-describedby`, set by `Field`), so screen readers read it with the field. Forms retain entered text and visibility choices after validation errors; passwords and provider keys are never copied into action state. Public links require HTTP(S), and external links use `noopener noreferrer nofollow`, except the link from a product page to its website: `websiteRel` in `src/lib/seo.ts` gives it `noopener` while the product's revenue is verified (shared or private), so search engines follow it and the founder's analytics see the referrer, and `noopener nofollow` otherwise. The site's `Referrer-Policy` (`strict-origin-when-cross-origin`) sends only the origin. Private editors require ownership even when accessed by a forged URL, and database RLS independently enforces ownership for direct API calls.

## Local and production Supabase

Development and tests use Supabase locally, in Docker through the Supabase CLI, configured by `supabase/config.toml` and the migrations. Production is the Supabase Cloud project `vgwgeennghaqpvfsqewq` in eu-central-1, which gets the same migrations through `supabase db push --linked` and the same Auth settings through `supabase config push`, with the overrides in `[remotes.production]`: the site URL and redirect URL on `thesaasharbor.com`, 60 seconds between emails to one address, and its own `HARBOR_PRODUCTION_SMTP_*` variables, so the per-machine SMTP settings in `supabase/.env.local` cannot reach it. `scripts/local-supabase.mjs` reads the local stack's URLs and keys from `supabase status` without printing them, refuses anything that is not on 127.0.0.1, and can start the stack. `npm run dev` runs `scripts/local-env.mjs` first, which starts the stack when needed and writes only the managed keys in `.env.local`. The app only needs the public Supabase variables plus the server-only secrets for revenue verification and the SMTP settings for notification emails, so it can later point at any Supabase instance, self-hosted or Cloud. Locally the notification emails go to Mailpit's SMTP port (55325, `[local_smtp]` in `config.toml`), which `scripts/local-env.mjs` writes into `.env.local` unless another SMTP server is set there.

## Scheduled jobs

The jobs run from the database, not from the host, so they work on any host and plan. Migration `20260926010000_scheduled_jobs.sql` enables pg_cron and pg_net and schedules `private.run_scheduled_job`, which queues a POST to the app with `Authorization: Bearer` and the secret: `/api/email/send` every minute (60-second timeout) and `/api/revenue/sync` every ten minutes (310 seconds, since a sync may run for five minutes); migration `20260926100000_domain_verification.sql` adds `/api/domains/check` every hour at 23 minutes past (70 seconds), and migration `20260928110000_telegram_alerts.sql` adds `/api/telegram/send` every minute (60 seconds). Four daily jobs run inside the database: `harbor-job-history` (03:17) deletes pg_cron's run history after a week, `harbor-telegram-retention` (03:29, migration `20261001190000_telegram_retention.sql`) gives up Telegram alerts that waited a day and deletes those handled a week ago, which the sending worker also does but never runs while Telegram is not set up, `harbor-analytics-retention` (03:41) deletes statistics after 25 months, and `harbor-unfinished-signups` (03:53) deletes unfinished sign-ups. pg_net drops its responses after six hours. The site address and the secret are the Vault secrets `harbor_site_url` and `harbor_cron_secret`, set only in production; without them the function returns null and calls nothing, so local stacks and CI stay quiet, and `npm run email:send` and `npm run revenue:sync` stand in locally. The function runs as the jobs' owner and no API role may execute it (`scheduling.test.sql`). Supabase's own setup lets the API roles execute pg_net's functions; they are unreachable through the API, since the `net` schema is not exposed, and a migration cannot revoke grants that `supabase_admin` made.

## Authentication and local tests

Authentication is Supabase Auth (email and password, at least `PASSWORD_MIN_LENGTH` characters, which `minimum_password_length` in `supabase/config.toml` repeats). On a site served over https, `authenticate` also refuses a sign-up whose email domain cannot receive email, from a DNS lookup of its MX records (`src/lib/email-domain.ts`); DNS failures let the sign-up through. Confirmation and password reset emails use the templates in `supabase/templates`, generated from `src/lib/email/auth-templates.ts` and checked by a unit test: the link carries a token hash and opens `/auth/confirm` on the address the app passed as the redirect URL, so the same templates serve the dev server, the browser tests and production. The confirm page verifies the token with `verifyOtp` only when the reader presses its button, so the link works in any browser (PKCE code links only worked in the browser that signed up) and email link scanners, which open links before people do, cannot use it up. Only the `email` and `recovery` types are accepted. A confirmed email leads to the product form while the account has no product, and to the dashboard after that; a recovery link leads to choosing a new password. Every way to list a product starts with an account: for visitors, the header's List your SaaS and the home page lead to `/auth?mode=signup`, and `/dashboard/saas/new` sends them there too, rather than to sign-in. The sign-up form links to sign-in for those who have an account.

The sign-in, sign-up and password reset forms (`src/components/auth-panel.tsx`) render on the `/auth` page for direct visits, reloads and links in emails, and in a dialog over the current page when a link inside the site leads to `/auth` (`src/app/@modal/(.)auth`, an intercepting route in the root layout's `@modal` parallel slot, drawn by `RouteDialog` in `src/components/route-dialog.tsx` with Radix Dialog, which the feedback dialog shares). Radix returns focus to its own trigger, which a dialog opened by an address does not have, so `RouteDialog` remembers the element that had focus when it opened and returns focus there on closing. The slot's `default.tsx`, `page.tsx` and `[...catchAll]` render nothing, so any other navigation, such as the redirect after signing in, closes the dialog. A page that needs sign-in (the dashboard, messages, reports, feedback, the admin panel and `/auth/finish`, `authNeedsFullPage` in `src/lib/auth.ts`) redirects visitors to `/auth` during a navigation inside the site, and the dialog would open over that same page, which redirects again, without end. When Next-Url names such a page, the intercepted route therefore loads the full `/auth` page instead (`FullPageLoad`). The full sign-in page counts as one too, so switching forms there loads the other form as a page rather than opening a dialog over the form it shows. Removing Next-Url in the proxy is no way out: the router then receives a response that does not match its cache and loops as well. Switching between the forms replaces the history entry, so closing the dialog (Escape, the close button or the backdrop) goes back to the page it opened over. Each form is keyed by its mode, since only the query changes and Next.js keeps a page's state across query changes, so a switch starts a fresh form instead of showing the last one's result, and the links between the forms keep `next`. Signing in replaces it too (`RedirectType.replace`), so going back, or closing a dialog that sign-in continued to, such as feedback, never returns to the sign-in form. With the slot beside it, the root layout's title template applies to the home page too, so the home page sets an absolute title.

Sign-in with Google and GitHub uses Supabase Auth's providers with the PKCE flow; `OAUTH_PROVIDERS` in `src/lib/auth.ts` lists them in button order. The sign-in and sign-up pages show a Continue with button (`ProviderButton`, with Google's four-color mark and GitHub's mark in the text color) for each provider Supabase's public `/auth/v1/settings` reports as enabled (`enabledProviders`, cached for a minute). Each is a plain link to `GET /auth/oauth/<provider>`: a link rather than a form, so the redirects to Supabase and the provider are navigations that the `form-action 'self'` policy does not cover, and not `next/link`, whose prefetch would start a sign-in. The route builds the provider's address with `signInWithOAuth` (the code verifier goes into a cookie), asks Google to let the user choose an account, and remembers in a ten-minute, http-only cookie on `/auth` the provider, where to continue (`next`, through `safeNext`) or, for a confirmation before deleting the account, which user must come back (for Google with that user's email as `login_hint`). The provider returns through Supabase to `GET /auth/callback`, which exchanges the code for the session. Its response carries `Referrer-Policy: no-referrer` (`next.config.ts`), which also governs the page its redirect leads to, so site statistics do not count that page as a visit from the provider. A new account continues to `/auth/finish`; a confirmation from a different account signs that session out and deletes nothing; everyone else continues to `next` or the start page. Failures come back as `/auth?error=failed`, `email` (the provider gave no verified email address, from Supabase's `error_code` or description), `unavailable` or `account`, with `provider`, which the sign-in page turns into fixed messages naming the provider. Supabase asks GitHub for the `user:email` scope and links a sign-in to an existing account with the same confirmed email address, so such users keep their password as well. The providers are configured in `[auth.external.google]` and `[auth.external.github]` with `HARBOR_GOOGLE_*` and `HARBOR_GITHUB_*` through `env()`, off by default, and for production in `[remotes.production.auth.external.*]` with `HARBOR_PRODUCTION_*`, which `npm run auth:production` fills. A new password is accepted only from a session opened from an email link in the last 15 minutes (the `otp` entry in the token's `amr` claim), and every other session of the account ends afterwards; the page sends no referrer, because its address holds the token. Redirect allowlists (`/auth/confirm` and `/auth/callback` for each app origin), the templates and subjects, email confirmation and the 6-character password minimum are set in `supabase/config.toml`; production Auth needs the same. By default every local email goes to Mailpit; `LOCAL_MAILPIT_URL` makes the sign-in pages link to it and is only honored for a loopback address. `[auth.email.smtp]` in `config.toml` reads `HARBOR_SMTP_*` through `env()`. The Supabase CLI resolves those from `supabase/.env` (committed defaults, real email off), then `supabase/.env.local` (git-ignored, per machine), then the process environment. `scripts/local-supabase.mjs` starts the stack with real email only when a password is present, can force Mailpit, and reads the running Auth container's SMTP host to report the active mode. The browser tests refuse to run unless email goes to Mailpit, so they can never email real addresses.

`scripts/test-local.mjs` obtains credentials and the Mailpit URL from the local CLI without printing them, refuses non-loopback addresses, and starts Playwright with a separate `.next-e2e` output. Its admin credential exists only in the test process. Email stays inside local Mailpit: the runner points the app's SMTP settings at it, whatever `.env.local` says, and makes message emails due at once, so the tests read notifications there. Tests remove their users and uploaded files afterward. The local stack uses its own port range (55320-55329) so it can run next to other local Supabase projects. Database access tests are a pgTAP suite (`supabase/tests/database`) that runs inside a rolled-back transaction and has no persistent test fixtures.

## Deliberate limits

There are no company profiles, transaction features, revenue integrations other than Stripe, Paddle, Polar, Dodo Payments, Creem, Chargebee, Whop, RevenueCat and Gumroad, or image garbage collector (replaced images stay until the account is deleted). Notification emails are in English only, and turning them off takes a sign-in: they carry no one-click unsubscribe header. Admins cannot remove a single message; suspending the sender hides the conversation instead. The first version is an owner-usable profile and discovery application. Real usage may warrant optimized images and cache design before broader public launch.
