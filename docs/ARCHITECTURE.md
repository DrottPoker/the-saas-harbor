# Architecture

One Next.js App Router application uses React, TypeScript, Tailwind CSS and shadcn/ui. Supabase provides PostgreSQL, email/password authentication and public image storage. Public pages use server rendering. Mutations use Server Actions with fresh `getUser()` checks; a Proxy refreshes the session cookies using `getClaims()`. `currentUser()` and the public detail loaders (`publicSaas`, `publicProfile`) are wrapped in React `cache()`, so the layout, `generateMetadata` and the page share one round trip per request. `error.tsx` offers `retry()`, which re-fetches server data, and `global-error.tsx` covers failures in the root layout.

## Data and authorization

| Resource                     | Public access                                               | Owner access                                                      |
| ---------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| `profiles`                   | Name, slug, headline, location, About, links, skills, photo | Insert/update own row, through `save_profile`                     |
| `profile_experience`         | Roles with dates                                            | Insert/delete own roles, through `save_profile`                   |
| `saas`                       | Product description, slug, category, website, logo, owner   | Insert/update/delete own products                                 |
| `reports`                    | None                                                        | Read reports they sent; write only through `submit_report`        |
| `moderation_log`             | None                                                        | None; admins read it                                              |
| `private.admins`             | None                                                        | None; granted with `set_admin` by the service role                |
| `notification_settings`      | None                                                        | Read own choices; write only through `save_notification_settings` |
| `private.email_outbox`       | None                                                        | None; only the service role claims and completes emails           |
| `saas_settings`              | None                                                        | Read/write own visibility choices and launch date                 |
| `revenue_connections`        | None                                                        | Read own provider, status and key hint; never the key             |
| `revenue_snapshots`          | None                                                        | Read own verified history; no writes                              |
| `public_metrics`             | Current shared, verified figures and shared launch date     | No writes; kept in sync by a trigger                              |
| `private.*`                  | None (schema not exposed)                                   | None                                                              |
| `public_saas`, `leaderboard` | Public projection with `revenue_status`                     | Same public fields                                                |
| `conversations`, `messages`  | None                                                        | Read conversations they are in; write only through `send_message` |
| `conversation_reads`         | None                                                        | Read/write own read position                                      |
| `blocks`                     | None                                                        | Read/insert/delete own blocks                                     |
| `inbox`                      | None                                                        | Own conversations with the latest message and unread count        |
| `profile-images`             | Image bytes are public                                      | Upload/delete only within own UUID prefix                         |

Every exposed table has RLS and explicit grants. Views use `security_invoker = true`. Composite foreign keys prevent attaching another owner's data to a product. Makers hold column grants on `profiles` and `saas` for exactly the fields they edit, so ids, `created_at` and the moderation columns are out of their reach; before these grants, a direct API insert could date a product into the future and keep it first in New arrivals. Hidden products and suspended profiles are left out of the public access above, and admins can read every row; see Reports and moderation. The invoker `save_saas` RPC saves product details, visibility choices and launch date; it accepts no figures. Verified figures are written only by trusted server code with the service-role key, through `record_revenue_verification`, which is executable by `service_role` alone.

`supabase/tests/database/privileges.test.sql` lists every table, column and function privilege that `anon` and `authenticated` hold in `public`, and fails on anything else, so a migration that forgets a revoke cannot expose a new object unnoticed. Since migration `20260925190000_release_hardening.sql`, objects created later in `public` get no privileges for those roles until a migration grants them; functions still need their own `revoke execute ... from public`, because Postgres grants EXECUTE to PUBLIC globally. The public views are read-only for both roles.

The public projection `public_metrics` is maintained by `private.refresh_public_metrics`, called from triggers on `saas_settings`, `revenue_snapshots` and `revenue_connections`. It and its trigger function are SECURITY DEFINER, because a maker's own setting change must update a table the maker cannot write. They live in the unexposed `private` schema, has an empty `search_path`, and its execute privilege is revoked from API roles. An unset sharing flag writes NULL into the projection. Snapshots carry an identity `seq` so "latest" is deterministic even for snapshots taken at the same instant.

Public reads deliberately create a separate anonymous Supabase client. They do not inherit the current owner's session. This makes the public route's data shape identical for an owner and a visitor. All application routes are dynamic; data fetches use `no-store`, and the Proxy sends `Cache-Control: private, no-store`. The embeddable badge is the exception: it shows only public figures and may be cached for ten minutes (see Addresses and sharing). No shared application/CDN cache holds private records. An already downloaded public page cannot be recalled from a visitor.

## Revenue and discovery

MRR is stored as integer USD cents (at most 999,999,999,999, below JavaScript's safe integer limit) and only ever comes from revenue verification through a payment provider; see below. Verified MRR, paying customers and launch date have independent visibility switches. A verification older than seven days is hidden by the `public_saas` view and marked `stale`, so it leaves the leaderboard. `revenue_status` is `verified`, `private`, `stale` or `unverified`. The MRR history (`mrr_history`, twelve month-end values) and 30-day growth (`mrr_growth_pct`) reveal MRR, so they are public only when MRR is shared and fresh.

The leaderboard is ordered in PostgreSQL by public MRR descending, then creation time ascending, then UUID ascending. Ties receive deterministic sequential positions. Category filters preserve the global rank. Browse includes products without shared MRR and orders by name. New arrivals orders by creation time descending. List queries return at most 12 rows per page. The server validates category and page inputs and searches product names case-insensitively. User-supplied wildcard characters (`%`, `_`, `*` and backslash) are removed first, since PostgREST treats `*` like `%`.

## Demo products

`src/lib/demo.ts` holds fifteen made-up products with makers, logos, descriptions and figures, so a first visitor sees what listings look like instead of an empty directory. They exist only in code, never in the database, so nothing that reads data (the ranking, the sitemap, maker pages, the admin panel, the sharing card's figures) can take them for real products.

- **When.** `demoActive()` in `src/lib/data.ts` counts the leaderboard. Demo products show while fewer than a page (12) of real products share verified MRR, and never with `DEMO_PRODUCTS=off`. When the count cannot be read, they stay hidden.
- **Where.** `Explore` asks `demoRows()` for the demo products that match the list's category and search, on the first page only, and only as many as the real products leave free on it, so each real product that joins takes one demo place. They follow the real products in their own section, headed Demo products, as a table on the leaderboard and as cards in Browse and New arrivals. The leaderboard takes only those that share MRR, highest first and without ranks; New arrivals orders them by launch date, since they never joined.
- **Marking.** Every row, card and page carries a Demo badge. Their revenue status is never `verified`, their figures never carry the verified mark and are called Demo MRR or made up, and they have no website, maker account or maker page, and no Send message or Report. Their logos are drawn in `src/components/demo-logo.tsx`, and their 12-month history is generated per month from a starting level, so charts and 30-day growth behave like real ones.
- **Pages.** `/demo/<slug>` renders the same `ProductProfile` component as `/saas/<slug>`, with a notice at the top and `noindex, nofollow`, and answers 404 once demo products are gone. How it works explains them while they show.
- **Removing them** for good means deleting `src/lib/demo.ts`, `demo-logo.tsx` and the `/demo` route, the demo functions in `data.ts`, the `demo` branches in `listings.tsx`, `explore.tsx` and `ProductProfile`, and their tests.

## Revenue verification

Makers connect one payment provider per product: Stripe, Paddle, Polar or Dodo Payments, each with a key that can only read (migration `20260925230000_payment_providers.sql` made the Stripe-only names provider-neutral). The flow lives in `src/lib/revenue`, with one folder per provider:

- `catalog.ts` names the providers and their key labels, for the browser as well. `providers.ts` maps each to its adapter (`types.ts`): `parseKey` validates a pasted key, and `read` reads the account and returns MRR per currency, paying customers, the counted subscription ids, what could not be counted, and service lines for the history (or none, with a note).
- `http.ts` sends only GET requests, with a timeout, and spaces requests to one provider at least 300 ms (Paddle, Dodo) or 150 ms (Polar) apart in each process: Paddle limits each IP address to 240 requests a minute, and Dodo and Polar each account. Overrides of the provider and exchange-rate addresses, used by the tests' fake server (`tests/e2e/fake-providers.mjs` and `fake-billing.mjs`), must be https in production; Paddle, Polar and Dodo add `/live` or `/test` to theirs.
- `money.ts` normalizes billing intervals to months (a day or week by the average month of 365.25 / 12 days) and converts per-currency totals to USD cents, rounding once. `history.ts` is pure and unit-tested: MRR at an instant is the sum of the paid recurring charges whose service period covers it, the way revenue analytics tools reconstruct it. Each provider turns its invoices, transactions or orders into service lines. The last twelve month-ends give the chart, and MRR from charges now against 30 days ago gives the 30-day growth, so both sides of the comparison use the same method. History is converted at today's rates, so the chart shows the business rather than currency moves.
- `fx.ts` converts other currencies to USD with Frankfurter's daily central-bank rates (base USD). A currency without a rate fails the verification instead of being dropped.
- `crypto.ts` stores keys with AES-256-GCM under `STRIPE_KEY_ENCRYPTION_KEY` (the name predates the other providers and stays, since changing the secret needs a re-encryption plan), bound to the SaaS id as associated data. The stored format carries a version prefix for later key rotation. Owners can never read the ciphertext: `encrypted_key` is excluded from their column grants.
- `sync.ts` verifies before storing anything, then calls `record_revenue_verification`, which stores the provider and key, claims the counted subscriptions, records a snapshot (with the provider, the history and the MRR from charges now and 30 days ago) and updates the connection in one transaction. A new key may switch the product to another provider; a re-verification must come from the connected one. A subscription can verify one SaaS only (`private.subscription_claims`, the SHA-256 of the subscription id, prefixed with the provider's name for providers other than Stripe), so one account cannot be counted twice. Failed re-verifications record a readable error for the owner and keep the last snapshot until it goes stale.

MRR has one definition for every provider: active and past-due subscriptions, their recurring charge normalized to a month, after ongoing discounts, before tax. Trials, paused subscriptions, one-time discounts and usage-based charges are excluded, and paying customers are customers with a subscription worth more than zero. What each provider gives decides how it is read:

- **Stripe** (`rk_live_`; `rk_test_` only when `REVENUE_ALLOW_TEST_KEYS=true`), with Read for Subscriptions, Invoices, Coupons and Prices. Secret and publishable keys are rejected. The editor links to Stripe's form for a new restricted key with the name and those four permissions filled in (`stripeKeyCreationUrl` in `stripe/key.ts`, with the ids `rak_subscription_read`, `rak_invoice_read`, `rak_coupon_read` and `rak_plan_read`, which Prices still use). Stripe does not document these parameters, so the editor also names the permissions to check. `stripe/client.ts` reads active and past-due subscriptions with expanded discounts, then the coupons and tiered prices they reference, and paid invoices from the last 25 months with all their lines and the prices those lines use; every request pins `Stripe-Version: 2026-08-26.dahlia`. `stripe/mrr.ts` values licensed items (per-unit and volume or graduated tiers, quantity transforms, forever and repeating discounts in percent or amount), and a multi-currency price by its amount in the subscription's currency (`currency_options`). `stripe/history.ts` counts each subscription line's net amount (after discounts and inclusive tax) over its service period, full periods by the price's billing interval and prorations at their share of the billing period they fall in. Invoice history is extra: a key without Invoices or Prices access, or an account with more invoices than one run reads (200 pages), still verifies MRR, and the note names the missing permission.
- **Paddle** Billing (`pdl_live_apikey_`; `pdl_sdbx_apikey_` only with test keys allowed), with Read for Subscriptions and Transactions. Legacy keys, which have full access, are rejected. Paddle bills in local prices and converted currencies and adds or includes tax when it bills, which a subscription's prices do not show, so `paddle/mrr.ts` values each active or past-due subscription by its latest paid transaction for a full billing period (lines with a recurring price and no proration, or a proration rate of 1): the line totals less tax, and without a discount that has ended since (the subscription has no discount, a one-off one, or one whose end has passed). A subscription without such a charge, such as one imported into Paddle, is not counted and the maker is told. Transactions from the last 25 months serve MRR and the history, where every recurring line counts over its period and a proration at the full period's rate. An account with more transactions than one run reads still verifies MRR from the window its subscriptions need, without history. Requests pin `Paddle-Version: 1`, and the cursor's next page is built from its `after` value, so requests only go to Paddle's own address.
- **Polar** (`polar_oat_` organization access tokens), with the scopes organizations:read, subscriptions:read and orders:read. Sandbox and production tokens look alike, so a new token is tried on production first and on the sandbox where test keys are allowed. `polar/mrr.ts` takes each active or past-due subscription's amount, which is its prices less its current discount and without metered usage, adds back a discount for the first period only, and takes out tax where prices included it, at the share the subscription's latest paid order shows (an order whose total equals its subtotal less discounts included tax). The history counts each item of paid subscription orders over its own period at the order's net share of its subtotal, which removes discounts and tax either way, leaving metered prices out. Requests pin `Polar-Version: 2026-10`.
- **Dodo Payments**, with a key whose write access is turned off. Dodo documents no key format, so only keys that plainly belong to another provider are refused, and the environment is found like Polar's. `dodo/mrr.ts` takes each active or past-due subscription's recurring charge (`recurring_pre_tax_amount`), leaving out trials, on-demand subscriptions and those on hold or paused. Where the charge includes tax, the tax is taken out at the share the subscription's latest successful payment shows, two requests each and at most 200 subscriptions a run. Dodo's payments do not say which period they cover, so these products have no history or 30-day growth.

Server actions in `src/app/revenue-actions.ts` check ownership on every call, since the SaaS id and the chosen provider are bound on the client, and validate the provider. Before reading an account they call `begin_revenue_check`, which counts every check, successful or not: a product is refreshed at most once per five minutes (from `last_synced_at` or `last_checked_at`), and a maker starts at most 20 checks an hour (`private.revenue_checks`, kept an hour). Makers see only failures written for them (`VerificationError` in `src/lib/revenue/errors.ts`, which provider request errors extend); anything else, such as a database error, is logged and shown as a generic failure. The editor's provider choice sits outside the key form, so the form's reset after each submission leaves it as it was. `POST /api/revenue/sync`, called with `Authorization: Bearer $CRON_SECRET` (compared in constant time), re-verifies the connections that are due (migration `20260925233000_hourly_verification.sql`). `claim_due_connections`, executable by `service_role` alone, claims one at a time for three workers: the connection verified or checked longest ago, once 55 minutes have passed, marking it checked with `for update skip locked` so an overlapping run skips it. A run claims nothing new after four minutes (`maxDuration` is 300 seconds), so Vercel Cron (`vercel.json`) calls it every ten minutes, with GET and the same header; each connection is then verified about every hour. A scheduled verification reads only what MRR needs and carries over the history and 30-day growth from the latest snapshot when the same provider gave them less than 23 hours ago (`history_at`), so the expensive reads happen about once a day; a maker's Refresh now and a new key read everything. `record_revenue_verification` replaces the day's snapshot (UTC) for a re-verification from the same provider instead of adding one, so a product keeps one snapshot per day; a new key always adds one. The projection's trigger runs on updates too. The service-role key (`SUPABASE_SECRET_KEY`) is only read by `src/lib/supabase/admin.ts`, a server-only module used for these trusted writes and for the email worker (see Notification emails).

## Deleting data

Makers delete their account under Maker profile → Delete account, confirming with their password. `deleteAccountAction` (`src/app/actions.ts`) calls `deleteAccount` in `src/lib/account.ts`:

1. It signs in again with the password on a separate client without cookies. Auth's rate limit applies, and a wrong password stops here with nothing changed.
2. With that fresh session it removes every file under the maker's folder in `profile-images` through the Storage API, repeating until the folder lists empty. Storage blocks SQL deletes on `storage.objects`, which has no foreign key to `auth.users`, so files would otherwise outlive the account. If this fails, the account stays in place and can be deleted again.
3. It calls `public.delete_account()`. This SECURITY DEFINER function deletes only `auth.uid()`, and only when the JWT's `amr` claim has a password sign-in from the last five minutes, so a leaked or long-lived session token alone cannot delete an account. It deletes the user's audit log entries (email and IP address), leftover refresh tokens and sign-in flows, then the auth user. Foreign keys cascade to the profile, products, settings, provider connections with their keys, subscription claims, snapshots, the public projection, the reports the maker sent, the reports and admin decisions about them, their admin rights, their email settings, the emails queued or sent to them, and their product additions and revenue checks. The function also deletes other makers' queued emails about the maker's messages and the live-update events that name the maker. Execute is granted to `authenticated` only.
4. The action signs the browser out and redirects to `/account-deleted`.

Makers delete a single product at the bottom of its editor by typing its name. `deleteSaasAction` checks ownership and the name, removes the logo through the Storage API unless the maker's profile photo or another of their products uses the same file, then deletes the row under the `saas_owner_delete` RLS policy. Foreign keys remove the settings, the public projection, the snapshots and the provider connection with its key and claims, which frees the provider account for another product. Referential actions run as the table owner, so makers still cannot write those tables directly. Logos replaced earlier are not tracked and stay until the account is deleted.

The pgTAP suite covers the recent-password requirement, who may delete a product, the complete removal and that other makers are untouched. The browser test covers both flows, including a logo that is also the profile photo and images in a subfolder.

The privacy policy is `src/app/privacy/page.tsx`. The operator's name and contact address come from `src/lib/legal.ts`; while they are unset, the page says it is a draft. Anything new that stores personal data must be described there and removed by account deletion, and product-scoped tables need an `on delete cascade` foreign key to `saas`.

## Maker profiles

Profiles are personal and entirely public, and laid out like product pages. `profiles` holds the name, a headline, a location, About (the `bio` column, up to 2,000 characters), links to a website, LinkedIn, GitHub, X and one other site, skills, and the path to the photo. `profile_experience` holds roles with months stored as the first day of the month; a role without an end month is current.

- `save_profile` saves the whole profile and replaces its roles in one transaction. It runs with the maker's rights, so RLS decides and a maker can only write their own profile. A trigger caps a profile at 40 roles however they are written.
- The database repeats the form's rules: skills are at most 20 unique labels of up to 40 characters (checked by `private.valid_labels`), and LinkedIn, GitHub and X links must use https and point to their own site. `profileSchema` in `src/lib/domain.ts` gives the readable messages first.
- The editor (`src/components/profile/profile-form.tsx`) keeps the roles in React state and sends them as JSON. It submits from `onSubmit` rather than the `action` prop, because React resets a form after its action, which would show stale values in controlled fields next to the state that is sent. File fields are cleared after a successful save instead.
- The public page (`src/app/users/[slug]/page.tsx`) follows the product page: a header with the photo, name, headline and location, a row of key figures (products, and verified MRR and paying customers summed over the products that share them, from `makerTotals`), then About, products and experience, with links and skills at the side. Roles are listed current first with LinkedIn-style durations. The owner sees Edit profile and a prompt for missing sections; everyone else sees Send message.

## Messages

Two makers share one conversation (`conversations`, with the participants in a fixed order and a unique pair), created with the first message. Only the two participants can read it, through RLS on `conversations` and `messages`. Everything references `profiles` with `on delete cascade`, so deleting either account deletes the whole conversation, for both makers.

- Writing: `public.send_message(recipient, body)` is the only write path. It is SECURITY DEFINER because makers cannot write these tables, always uses `auth.uid()` as the sender, trims the text (1 to 4,000 characters), requires profiles on both sides, refuses blocked pairs in either direction, and limits each sender to 20 messages a minute, 500 a day and 20 new conversations a day; an advisory lock per sender makes parallel requests count one at a time. A deleted and a suspended recipient get the same answer, so a sender cannot tell a suspension. Errors meant for makers use SQLSTATE P0001; `sendMessageAction` shows those and a generic message for anything else.
- Reading position: `conversation_reads` stores how far each maker has read, never shown to the other maker, so there are no read receipts. `mark_conversation_read` only moves it forward and never past the current time; the view `inbox` and `unread_message_count()` use it.
- Live updates: a trigger announces each new message with `realtime.send` on the private Realtime channels `user:<recipient>` and `user:<sender>`. The event carries ids only, never the text, and an RLS policy on `realtime.messages` lets a maker join only their own channel. `src/components/messages/live.ts` keeps one channel per tab for the header count and the open conversation. The conversation then reads the new message under RLS with the browser client (`src/lib/supabase/browser.ts`), and catches up, reading everything after the newest message on screen, when a hidden tab becomes visible again or the channel joins again after the connection dropped; the header then counts again too. Writes always go through Server Actions.
- The header's unread count is rendered on the server and refreshed on new messages and after reading; the most recently requested count wins. Times are formatted in the visitor's time zone after hydration (`LocalTime`).
- Send message on maker profiles and product pages opens `/messages/<maker id>`. Visitors go to sign-in with `next`, which `safeNext()` limits to the messaging and report pages, so it cannot send anyone to another site.
- A suspended account can neither send nor receive messages (`send_message` checks both sides), and its conversations leave the other maker's inbox and unread count, because both read the other maker's profile under RLS.
- A maker who has not read a new message within five minutes gets one email about the conversation, which names the sender and never contains the text (see Notification emails).

## Reports and moderation

Migration `20260925120000_moderation.sql` adds reports, admin decisions and product limits. The admin panel lives under `/admin`.

- **Admins** are rows in `private.admins`. The app never grants them: `public.set_admin(email, admin)` and `public.list_admins()` are executable by `service_role` only, for `npm run admin` and operators. `public.is_admin()` answers for the caller and is executable by both API roles, because RLS policies call it. Admin functions start with `private.require_admin()`.
- **Visibility.** `saas` rows are public while `hidden_at` is null and the owner's profile is not suspended; `profiles` and `profile_experience` while the profile is not suspended; `public_metrics` exactly when its product is visible (the policy's subquery runs under the `saas` policy). Owners always see their own rows, and admins see every row. Because `public_saas` and `leaderboard` run with the caller's rights, hidden products leave every listing and the ranking without changes to the views. The moderation columns live on `saas` and `profiles`, so the owner reads the reason and explanation from their own row, and nobody else can see a hidden row at all.
- **Reports** are written only by `submit_report(target, id, reason, details)`, a SECURITY DEFINER function. A reporter can report a product or profile that is listed, or a message they received: the message is looked up together with its conversation and the reporter must be one of its two makers, so admins never read a conversation, only the copy of a reported message. Each report stores a copy of what was reported in `content`, so a later edit cannot hide it. Makers cannot report themselves; suspended accounts cannot report; there is one open report per reporter and thing (partial unique indexes); and an account sends at most 10 reports an hour and 30 a day. Illegal content and Something else need an explanation. Reporters read their own reports under RLS (`reporter_id`), admins read all, and the reported maker never sees who reported. `reports` has no column naming the admin who decided, so reporters cannot learn who the admins are.
- **Decisions** go through `admin_hide_saas`, `admin_restore_saas`, `admin_suspend_account`, `admin_restore_account` and `admin_dismiss_report`, all SECURITY DEFINER. Hiding and suspending need a reason from the same list as reports (the `public.moderation_reason` domain, mirrored in `src/lib/moderation.ts`) and an explanation, which the maker sees in their dashboard and editors as a statement of reasons, with how to disagree. Hiding closes the open reports about the product; suspending closes every open report about the maker. Admins cannot suspend themselves or another admin. Every decision is written to `moderation_log` with the admin, the reason, the note and the product or maker name at the time; only admins can read it. The maker is emailed about the decision, and reporters about the outcome (see Notification emails).
- **Admin panel.** `requireAdmin()` in `src/lib/admin.ts` answers a 404 for everyone but admins. It runs in the admin layout and again in every page, because a layout does not guard the segments below it, and every admin Server Action checks `adminSession()`. Pages read through the admin's own session under RLS. The one exception is account data in `auth.users`, which `admin_accounts(search, filter)` and `admin_account(id)` return after checking admin rights. Decision forms return to their page with `?done=` and a confirmation; `safeAdminPath()` limits where they may return to.
- **Product limits.** The `saas_limit` trigger allows 20 products per account and 5 new ones a day, however they are written. Additions are counted in `private.saas_additions`, kept a day, which deleting a product does not shorten, so deleting and adding again does not reset the day. An advisory lock per owner makes concurrent inserts wait for each other, so the limits hold exactly. `submit_report` counts a reporter's reports under the same kind of lock. The editor shows the limit before a maker fills in the form.
- **Deletion.** A report is deleted when either the reporter's or the reported maker's account is deleted. Deleting the reported product or message keeps the report and its copy (`on delete set null`), so a maker cannot make a report disappear by deleting the product. `moderation_log` entries are deleted with the account they concern and keep no name once the admin who decided deletes their account. `private.admins` rows go with the account.

The privacy policy describes all of this, and the terms at `/terms` list what is not allowed and how decisions and appeals work. Both are drafts until the operator is named in `src/lib/legal.ts`.

## Notification emails

Migration `20260925170000_email_notifications.sql` adds an outbox. Triggers queue each email in `private.email_outbox` in the same transaction as what it is about, so an email is neither lost when sending fails nor queued for something that was rolled back. A row holds the recipient's id, the kind, a topic and ids, never an address or message text.

- **What queues an email.** A new message queues one email per conversation for the recipient, unless they turned message emails off or an email for the conversation was already queued since they last read it. The email is queued at the message's own time, which is also what reading the message records, so the next message after a read always queues a new email; an advisory lock keeps two messages at the same moment from queuing two. A new report queues an email to each admin who wants them, unless one is waiting, due no earlier than an hour after the last one sent. A report that leaves `open` queues the outcome for its reporter. A `moderation_log` entry for hiding or restoring a product, or suspending or restoring an account, queues an email to the maker with the reason, and for hiding and suspending the explanation; notes on reversals are for admins only.
- **Settings.** `notification_settings` holds whether a maker wants message emails and, for admins, report emails; no row means both. Makers read their own row and write it only through `save_notification_settings`. Decision and outcome emails concern the maker's own content or report, so they are always sent.
- **Claiming.** `claim_emails(limit, message_delay)` and `complete_email(id, status, error)` are executable by `service_role` alone. `claim_emails` takes due rows with `for update skip locked`, locks them for two minutes, and returns the address with what the email needs at that moment (`private.email_context`): current names, the number of unread messages or open reports, and whether the recipient still wants it. A message email is due `MESSAGE_EMAIL_DELAY_SECONDS` (default 300) after it was queued, so makers who are online read the message first. It is skipped at sending when the conversation has been read since it was queued (a later message queued its own email), the two makers blocked each other, or the sender was suspended. `complete_email` records the outcome and tries a failed email again after 5, 10, 15 and 20 minutes before giving up. `claim_emails` also deletes emails a week after they were processed.
- **Sending.** `deliverEmails` in `src/lib/email/outbox.ts` claims one email at a time, renders it with `templates.ts` (plain text and escaped HTML, subjects on one line, footers that link to the settings or the terms) and sends it with nodemailer over one SMTP connection per run. A remote SMTP server must switch to TLS before the password is sent. A run claims nothing new after a minute and every SMTP step gives up after 15 seconds, so an email is never claimed again while it is being sent. Server Actions that queue an email call `sendQueuedEmails()`, which runs the worker after the response with `after()`. `POST /api/email/send` runs it for up to 100 emails when called with `Authorization: Bearer $CRON_SECRET` (compared in constant time by `src/lib/cron.ts`, like the revenue sync); production calls it every minute, for the delayed message emails, through Vercel Cron (`vercel.json`), which sends GET with the same header. Without `SMTP_HOST` and `EMAIL_FROM` the worker claims nothing and emails wait. Addresses and message text are never logged.

## Addresses and sharing

Products live at `/saas/<slug>` and makers at `/users/<slug>` (migration `20260925150000_slugs.sql`); `next.config.ts` redirects the earlier `/makers/...` addresses permanently. Triggers make the slug from the name (lowercase, accents removed with `unaccent`, words joined by hyphens, at most 60 characters) and add `-2`, `-3` and so on when it is taken; makers hold no grant on the column. Saving the same name at the same moment is serialized with an advisory lock. A renamed product keeps its five latest earlier slugs in `private.saas_slug_redirects`, and `saas_slug_redirect()` answers them only while the product is listed. A slug in use always wins over a redirect: a new product may take a slug that only redirects, and the redirect goes, so renaming cannot reserve names for later. A renamed maker does not keep the old slug: it is made from the person's name, which should not stay reachable after a change, and it is released at once. Deleting a product or an account frees its slugs.

The proxy answers links with an id, and addresses with capital letters, with a permanent 308 redirect before rendering, because a page that streams under `loading.tsx` can only redirect in the browser; it looks up only id-shaped addresses, as a visitor would. An earlier product slug redirects from the page itself (`findSaas` in `src/lib/data.ts`), which is rare enough for a browser-side redirect. Private areas, such as messages, reports and the admin panel, keep using ids.

`metadataBase` comes from `NEXT_PUBLIC_SITE_URL` (`src/lib/seo.ts`), so canonical links, the sitemap and sharing images use the public origin. Product and maker pages set their canonical address and Open Graph and Twitter card metadata through `pageMetadata()`; list pages point search and filter variants at their plain address. `opengraph-image.tsx` for products, makers and the site draws a 1200 × 630 card with `next/og` in the Geist it bundles (`src/components/og-card.tsx`): name, tagline or headline, logo or photo (PNG and JPEG; WebP shows initials, as Satori cannot draw it), and only the figures the page shows publicly. The badge at `/saas/<slug>/badge.svg` (`src/lib/badge.ts`, served by a route handler) is an SVG makers embed on their own sites, linked to the product page. It shows the product's MRR only while `public_saas` has it as `verified`, and otherwise says Listed on The SaaS Harbor; it holds no text a maker wrote. `?theme=dark` gives the dark colors, which repeat the surface tokens, since an image on another site cannot read `globals.css`. Text is measured with Helvetica widths and drawn with `textLength`, so a fallback font keeps the layout. An id, an earlier slug or capital letters redirect to the current badge, and hidden products and unknown slugs answer 404. The proxy's matcher leaves the path out, so the route sets its own headers: `Cache-Control: public, max-age=600`, `Content-Security-Policy: default-src 'none'`, `Cross-Origin-Resource-Policy: cross-origin` and `X-Robots-Tag: noindex`. The product editor previews it and gives the HTML and Markdown to paste (`src/components/badge-embed.tsx`). `sitemap.xml` lists the static pages, every listed product and the makers behind them, read as a visitor a thousand at a time (the API's row limit), so hidden products and suspended makers never appear; `robots.txt` keeps crawlers out of the dashboard, admin panel, messages, reports, sign-in and the API.

## Search engines and AI assistants

- **Category pages.** `/categories` lists the categories with their counts, and `/categories/<slug>` (the name in lowercase with hyphens, `categorySlug` in `domain.ts`) shows the category's ranked products as a leaderboard, then its other products A to Z, one page each with a link to the full list. Demo products are left out, since these pages are meant for search engines. The counts come from the `category_counts` view (migration `20260925210000_category_counts.sql`), which groups `public_saas` with the caller's rights, so hidden products and suspended makers never count. A category without listed products answers with `noindex` and is left out of the sitemap. Product pages link to their category page, and the footer to `/categories`.
- **Structured data.** `src/lib/structured-data.ts` builds schema.org JSON-LD, which `src/components/json-ld.tsx` renders with the request's nonce: `WebSite` on the home page, a `WebPage` with a `SoftwareApplication` and breadcrumbs on product pages, `ProfilePage` with a `Person` on maker pages, and `CollectionPage` with an `ItemList` on the category pages. It repeats only what the page shows, never demo products, and `<` is escaped so the data cannot close its element.
- **Titles.** A product that shares fresh verified MRR has it in its title and description, such as "QueryBird: $4,200 verified MRR".
- **llms.txt and Markdown.** `/llms.txt` (llmstxt.org) describes the site, how revenue is verified, the categories with their counts and the top 50 of the leaderboard. Every product and maker page has a Markdown version at its address with `.md` added: the proxy rewrites `/saas/<slug>.md` and `/users/<slug>.md` to route handlers under `/md/`, which answer ids, earlier slugs and capital letters with a redirect to the current `.md` address, like the pages. Pages announce their Markdown version with `<link rel="alternate" type="text/markdown">`. `src/lib/markdown.ts` writes them with exactly what the HTML pages show; text makers wrote is escaped so it cannot add headings, links or other structure, and each file and llms.txt say which parts makers wrote and that they are not instructions. They answer with `X-Robots-Tag: noindex` and a canonical `Link` to the HTML page, and `robots.txt` keeps crawlers out of `/md/`.

## Statistics

`/stats` adds up the leaderboard's figures. `public.directory_stats()` (migration `20260925220000_directory_stats.sql`) computes them in one query and returns JSON: the number of ranked products, combined and median MRR, paying customers summed over the products that share them, five MRR buckets (always all five), each category's count, combined and median MRR, the 30-day change (median and how many grow, shrink or stay), four bands of time since launch from shared launch dates, the month-end history summed over the ranked products for the months every one of them covers, and the five fastest growing products with at least $1,000 MRR. It is `security invoker` and reads `leaderboard`, so only shared, fresh, verified figures of listed products count, the same figures the leaderboard shows one by one; demo products never do. `parseStats` in `src/lib/stats.ts` validates the result, so a malformed answer fails instead of showing a wrong figure. Below five ranked products (`STATS_MINIMUM`) the page and its sharing card show no figures. The distributions are bar lists (`charts/bar-list.tsx`) in `--chart-1` with the value in text at each bar's end, and the history reuses the product page's chart with its table view.

## Security headers

Session cookies carry `Secure` whenever `NEXT_PUBLIC_SITE_URL` is https (`cookieOptions` in `src/lib/supabase/config.ts`, used by the server, the proxy and the browser client). The proxy's permanent redirects from an id to a slug are not cached, since a maker's slug follows their name. `src/proxy.ts` sets a Content Security Policy on every response, built by `src/lib/csp.ts` with a fresh 128-bit nonce per request. Scripts run only with that nonce (`'strict-dynamic'` lets them load their own chunks); Next.js reads the nonce from the request's policy and puts it on its framework scripts, and the root layout reads `x-nonce` for the inline theme script. `'unsafe-eval'` is allowed only in development, where React needs it. Styles allow inline use, because React writes `style` attributes, which a nonce cannot cover. Images may come from Supabase Storage, and the browser may connect to Supabase and its Realtime websocket; nothing else is allowed from other origins. Framing, plugins, foreign form targets and `<base>` changes are refused, and requests are upgraded to https when the site is served over https. A nonce requires dynamic rendering, which every route already uses. `next.config.ts` adds `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, and in production `Strict-Transport-Security` (two years, without subdomains, which may belong to other services). The browser tests fail on any console report of a blocked resource, and check that each response has a new nonce. `global-error.tsx` has no inline script, because a client component cannot read the nonce; its theme follows the operating system.

## Interface

On the site people are users, and a user is the founder of the products they own: product pages, cards, sharing cards and the Markdown call the owner founder, and everything else says user or profile. Code, the database and these documents keep the older word maker for the same person.

Styling uses Tailwind utilities in the components. Design tokens (colors, fonts, radii) live as CSS variables in `src/app/globals.css` and map to Tailwind names such as `bg-muted`, `text-muted-foreground` and `text-brand`. There is no page-specific global CSS. The type is Geist, loaded with `next/font`, and body text is never smaller than 12 px. The palette is neutral with one teal accent (`--accent`) for links, focus rings and checkboxes, and separate `--logo-*` tokens for the logo. The logo is a lighthouse above a rising bar chart and the sea, drawn once in `src/lib/logo.ts`: the header, footer and sign-in pages render it with the tokens (`src/components/logo.tsx`), and the favicon (`src/app/icon.svg`, which follows the browser's color scheme), sharing images and badge use the same colors from `LOGO_COLORS`. A unit test keeps those colors equal to the tokens and `icon.svg` equal to the generated mark; `npx vitest run -u` rewrites the favicon after the logo changes. Cards, tables and fields sit on `bg-surface`, one step lighter than the page background. Primary buttons use the foreground color. Destructive buttons use `--destructive` with `--destructive-foreground`, which is dark in the dark theme because white text on the lighter red there fails contrast.

There are two themes, light (warm paper, `#f6f5f1`) and dark (graphite, `#1b1f24`), and neither is pure white or black. `globals.css` defines each token once for light and once inside `@variant dark`. The custom `dark` variant matches `data-theme="dark"` on `<html>`, or the OS dark preference when light was not chosen, so "System" needs no JavaScript. The choice is stored in a `theme` cookie by the theme menu (`src/components/theme-menu.tsx`). A small inline script from `src/lib/theme.ts` runs in `<head>` before first paint and sets `data-theme` from the cookie, following the Next.js guide on preventing flash before hydration. The server never reads the cookie, so the theme does not stop pages from being cached later. `color-scheme` follows the theme, so native controls such as the date picker and scrollbars match. Components should rarely need `dark:` utilities, because the tokens switch instead.

Shared building blocks live in `src/components`: `site-chrome.tsx` (header and footer), `shell.tsx` (page width, page header, notices, empty states), `listings.tsx` (leaderboard, product cards, pagination), `product-profile.tsx` (the product page, for real and demo products), `avatars.tsx` (rounded-square product logos, round person avatars), `forms.tsx` (settings-style form sections) and `charts/` (revenue charts).

Charts follow one set of rules. `src/lib/charts.ts` builds chart models on the server (the zero-based axis with round steps, month names, whole-dollar labels), so client code never formats numbers. The product page shows MRR at month end as an area chart (`charts/mrr-chart.tsx`): a client component for the crosshair, the tooltip and reading months with the arrow keys, laid out in percentages so it renders on the server at any width without measuring. A table of the same values sits under it. Leaderboard rows show a 12-month sparkline (muted line, latest month in the accent; its range spans at least 30% of the peak so small wobbles stay small) and the 30-day growth, whose direction is carried by an arrow and a sign as well as by color. Chart colors are the `--chart-1` and `--chart-muted` tokens, checked for lightness, chroma and at least 3:1 contrast on the surface in both themes. Copy is plain and specific, without metaphors. Product logos next to a visible name are decorative (`alt=""`); the maker page avatar carries the maker's name.

## Images and forms

The server validates PNG/JPEG/WebP signatures, the 2 MB limit and a size of at most 4096 pixels on each side (read from the header by `src/lib/image-format.ts`, since a small file can unpack to a huge picture) before uploading an immutable random filename under the authenticated user's prefix. SVG is excluded. A check constraint limits stored image paths to a file directly in the owner's folder with an image extension. Makers can still upload to their own folder straight through the Storage API, which checks only the declared type and size, so the signature and size checks apply to uploads through the app. Storage enforces the matching MIME/size and ownership policies. Failed database saves remove their newly uploaded file. Replacing or removing a displayed image leaves previous uploads in storage in this first version; a future referenced-file cleanup job can remove them safely.

Validation runs on the server. Forms retain entered text and visibility choices after validation errors; passwords and provider keys are never copied into action state. Public links require HTTP(S), and external links use `noopener noreferrer nofollow`. Private editors require ownership even when accessed by a forged URL, and database RLS independently enforces ownership for direct API calls.

## Local and production Supabase

Development and tests use Supabase locally, in Docker through the Supabase CLI, configured by `supabase/config.toml` and the migrations. Production is the Supabase Cloud project `vgwgeennghaqpvfsqewq` in eu-central-1, which gets the same migrations through `supabase db push --linked` and the same Auth settings through `supabase config push`, with the overrides in `[remotes.production]`: the site URL and redirect URL on `thesaasharbor.com`, 60 seconds between emails to one address, and its own `HARBOR_PRODUCTION_SMTP_*` variables, so the per-machine SMTP settings in `supabase/.env.local` cannot reach it. `scripts/local-supabase.mjs` reads the local stack's URLs and keys from `supabase status` without printing them, refuses anything that is not on 127.0.0.1, and can start the stack. `npm run dev` runs `scripts/local-env.mjs` first, which starts the stack when needed and writes only the managed keys in `.env.local`. The app only needs the public Supabase variables plus the server-only secrets for revenue verification and the SMTP settings for notification emails, so it can later point at any Supabase instance, self-hosted or Cloud. Locally the notification emails go to Mailpit's SMTP port (55325, `[local_smtp]` in `config.toml`), which `scripts/local-env.mjs` writes into `.env.local` unless another SMTP server is set there.

## Authentication and local tests

Authentication is Supabase Auth (email and password). Confirmation and password reset emails use the templates in `supabase/templates`: the link carries a token hash and opens `/auth/confirm` on the address the app passed as the redirect URL, so the same templates serve the dev server, the browser tests and production. The confirm page verifies the token with `verifyOtp` only when the reader presses its button, so the link works in any browser (PKCE code links only worked in the browser that signed up) and email link scanners, which open links before people do, cannot use it up. Only the `email` and `recovery` types are accepted, and they lead to the dashboard or to choosing a new password. A new password is accepted only from a session opened from an email link in the last 15 minutes (the `otp` entry in the token's `amr` claim), and every other session of the account ends afterwards; the page sends no referrer, because its address holds the token. Redirect allowlists (`/auth/confirm` for each app origin), the templates and subjects, email confirmation and the 12-character password minimum are set in `supabase/config.toml`; production Auth needs the same. By default every local email goes to Mailpit; `LOCAL_MAILPIT_URL` makes the sign-in pages link to it and is only honored for a loopback address. `[auth.email.smtp]` in `config.toml` reads `HARBOR_SMTP_*` through `env()`. The Supabase CLI resolves those from `supabase/.env` (committed defaults, real email off), then `supabase/.env.local` (git-ignored, per machine), then the process environment. `scripts/local-supabase.mjs` starts the stack with real email only when a password is present, can force Mailpit, and reads the running Auth container's SMTP host to report the active mode. The browser tests refuse to run unless email goes to Mailpit, so they can never email real addresses.

`scripts/test-local.mjs` obtains credentials and the Mailpit URL from the local CLI without printing them, refuses non-loopback addresses, and starts Playwright with a separate `.next-e2e` output. Its admin credential exists only in the test process. Email stays inside local Mailpit: the runner points the app's SMTP settings at it, whatever `.env.local` says, and makes message emails due at once, so the tests read notifications there. Tests remove their users and uploaded files afterward. The local stack uses its own port range (55320-55329) so it can run next to other local Supabase projects. Database access tests are a pgTAP suite (`supabase/tests/database`) that runs inside a rolled-back transaction and has no persistent test fixtures.

## Deliberate limits

There are no company profiles, transaction features, revenue integrations other than Stripe, Paddle, Polar and Dodo Payments, or image garbage collector (replaced images stay until the account is deleted). Notification emails are in English only, and turning them off takes a sign-in: they carry no one-click unsubscribe header. Admins cannot remove a single message; suspending the sender hides the conversation instead. The first version is an owner-usable profile and discovery application. Real usage may warrant optimized images and cache design before broader public launch.
